## What it is

The object at 0x002CD138 is a `GmNameMap` subclass (vftable 0x00277B60, 0x14 bytes) that start-up makes in `GmHistoryLogsInit` (0x0006C3E0) with `Init(20)` and keeps at +0x04 of the logs. Each design data registry the game loads goes into it under a short name taken from its file: InstanceRegistries items (`GmRegistryItem::Run`, 0x001B49FC), start-up's library root (master's `App::LoadRegistries`, which calls it "Library"), the level manager's registry (0x0013DACB, a level's own `.ADR`) and six other callers. Other code releases them (eleven callers, the level manifest's Free among them).

It has **no lookup of its own**. Game code calls the inherited `GmNameMap::Find` (0x00025150, already recovered) on `s_instance` with a name ("Instance" at 0x000AFB06, "SaveData" at 0x0016B7D0, a record's type name at 0x00174DA6, 0x00174FD5, 0x00179163), then reads the registry with `AtDataRegistry::ValueAtPath` 0x00068860 or `ValueNamed` 0x00067CB0. Those two belong to the design data branch (worktree-agent-ab169319436606eee, datalookup). Nothing here needs them, so nothing is declared or recovered again.

## Quirks kept

* The key is the file name, cut at the first ".a" **anywhere** in it. Failing that, at the first ".A", then ".b", then ".B". The cut goes by that search order, not by position: `One.Ab\Two.a` gives "Two", and `Dir.adr\Inner\Leaf.ADR` gives "Dir". After the cut, the key is what follows the last backslash, at most eight bytes, with no terminator when it is eight long. The file name is first copied into 0x100 bytes on the stack, with no limit.
* The key is copied through its terminator and no further. Its other bytes are whatever was on Add's stack, and they reach the map's slot whole (the map copies eight bytes).
* A name already in the map is reported ("Duplicate name encountered", which ends the game) and is then added again.
* Release looks the registry up by value (`GetNameOf`) and then removes **by name**. Of two registries under one name, it removes the first the probe meets, which may be the other one. For a registry the map does not hold, it removes an empty name. That name's hash reads Release's uninitialised stack. The map's Remove then matches the first free slot that never held a name, and puts back the run of slots after it.
* The destructor clears `s_instance` even when another map is the instance.

## Oracle

`tests/oracle/oracle_regnames.cpp`, suite `regnames`. Cases:

* Every real `.MNG` with InstanceRegistries (31), in both spellings: a fresh map given "Library", then each registry, then each looked up by its key. "Instance" is also looked up. Then each is released in the file's order, as Free does, and looked up again. Then the map is destroyed through slot 0.
* Every `.ADR` path on the disc (103), in two cases, into one map that grows. The disc has leaf names in common, so duplicates are reported. The registries are looked up, released by thirds, and the map is destroyed with the complete destructor.
* 36 written file names plus a 255-character one, for every way KeyFor cuts and copies. Each goes through KeyFor alone, under three stack fills and two fills of the output, comparing 12 bytes. Then all go into one map and come out backwards.
* Duplicates: one registry twice, and two under one name, with each released first.
* Releasing what is not there: from an empty map, one never added, one released twice, and one whose own key is empty, each under three stack fills.
* The life cycle: made on filled and zeroed memory; Init with no table, with one, with 0 and with 40; Clear through slot 1, twice; a second map taking the instance; the first destroyed through slot 0 without freeing; the second destroyed and freed.
* Init with no heap, and with no memory.

Compared after each step: the vftable (as this class's or the name map's), `s_instance`, size, the table, next, group, every slot's value and all eight bytes of its name, Find's answers, and the heap calls and reports in order.

Add and Release keep eight bytes of name on their stack. They are called through a naked thunk that fills the 0x2000 bytes below with one byte, the same on both sides, and then calls from that depth. So the bytes past a short name's terminator are the same on both sides and are compared. A first try, with a fill function called before the call, left a harness return address in the original Add's name: the compiler had pushed the call's argument before calling the fill.
