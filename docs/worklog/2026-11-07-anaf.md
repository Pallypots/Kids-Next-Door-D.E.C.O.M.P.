* **The physical controllers and the device are this file's fakes, on both sides.** No class deriving from `AtInputController` other than `AtAbstractController` is recovered, nor the device (`AtInputOwner::m_device`). `AtInputPhysicalController` and `AtInputDevice` are shapes: a vbptr at +4, and slots 18 to 23. They hold what the original's binding code reads. What a real keyboard or pad does is not run.
* **Nothing recovered calls `AtInputMapper::Bind` or fills a controller's receivers.** Its callers are 0x0006CBE6 and 0x0006CE06, in the unrecovered owner, and the receivers' Add is at 0x00072574 and 0x0007269A. The oracle calls Bind directly, and adds receivers by hand.
* **Events are seven words the harness made up.** Nothing that makes a real event is recovered: 0x00079B40, 0x000783A0.
* **A real file reaches little.** ABSTRACT.ANA has 16 controllers: 3 to 64 buttons, 0 to 11 axes, `EventHandlers` 1 or 3, `DeadZone` 15, 20 or 25, `Saturation` always 95. **No POV count is ever above 0**, and there is no `NameSpace`. POVs, what the file does not use, and every error path rest on written text.
* The tokenizers on both sides are recovered ones, as in the earlier suites; the tok suite is what establishes them.
* **Not compared: a queue's second Allocate through stale pointers.** A controller's `Release` does not touch its queue, so a later `Init` links new nodes to freed ones and writes into them. Both would, but where the heap puts things differs, so the harness compares that the pointers are kept and clears them. Same reason as `AtInputRouter::Allocate` twice in the `ana` worklog.
* **Not compared: a controller whose name is not a string,** `ExpectName` leaving stack bytes, as for `.ANM`. Not in the written cases.
* NaNs that differ only in sign count as alike in the filter: that sign is the x87's, by operand order.
* `AtDeleteArray` stands for the original's `eh vector destructor` and its deleting forms' array path. `0x00073570` and `0x00079440` are called with flags 1 and 0 directly; flag 3 is only reached through `Clear` and `Release`, on the array.

## Why every loader's closure reaches the same 39 functions

It is the fatal report, not input.

Every loader has `if (status != 0) report "%s.%s"` on a failed open. That is `0x00014230`, then `0x000141C0`, then `0x00011070`, `AtFatal`. `AtFatal` does three things before it stops the machine:

1. Stops rumble: for each of the game's players, every playing force effect is reset (0x0006D7E0, 0x00073E00, 0x00074930), then the input system is advanced 10 seconds (0x0008F4F0 and 0x0006DA50 give the input system, 0x0006DEA0, 0x00024B70, 0x0006CE30, 0x0006D810, 0x00072610, 0x00072A30, 0x00073E20, 0x00073E60, 0x00073F00, 0x000B9A90, 0x000ED690) so the motors get told.
2. Draws the error screen in a loop that never ends, if there is a device to draw on (0x0008E2B0: text by language, via 0x00013F00; 0x00037EB0, 0x000582F0, 0x0005F600, 0x00042170, 0x000421A0, 0x00042280, 0x00023CB0, 0x00035840, 0x000358D0, 0x000412D0, 0x00041380).
3. If it comes back, prints, and launches back out: 0x00085197.

So the closure says nothing about what a loader needs. A seam at `AtFatal` cuts all 39, and that is the seam already in place: `platform/fatal.cpp` in the host build, the doubles in the oracles. **Other agents can leave them behind `AtFatal` and need no seam of their own.** The input code is on that path only for stopping rumble, which is why .ANA looked as if it shared them.

Of the 39: 32 are the game's, 7 are the library's. 0x00072A30 is recovered here. The other 31 are not: 3 report (0x00014230 and 0x000141C0 exist only as the two forms in `AtText.h`), 15 rumble, 13 screen. They belong with the rumble and with the 2D text, not with .ANA, and they are past the budget.

### Library, not game code

0x00085197, 0x000851D9, 0x000852BA, 0x00088047, 0x000880D9, 0x000882DC, 0x000885C2. Inferred to be XAPI's image launching, `XLaunchNewImage` and what it calls. Not recovered, and should not be, or counted in the game's denominator.

Evidence:
* Not on 16-byte boundaries, unlike the game's code, and `__stdcall` throughout.
* 0x000882DC builds `\Device\Harddisk0\Partition1\TDATA\%08x\$u\%s` from the title id it reads through the XBE header's certificate pointer at 0x00010118.
* Kernel imports: 0x00085xxx and 0x00088xxx call ordinals 49 `HalReturnToFirmware`, 165 `MmAllocateContiguousMemory`, 178 `MmPersistContiguousMemory`, 187 `NtClose`, 203 `NtOpenSymbolicLinkObject`, 215 `NtQuerySymbolicLinkObject`, 301 `RtlNtStatusToDosError`, and use `\Device\Cdrom0`.
* 0x000885C2 uses an SEH prolog from the C runtime's range, 0x00126D08.

The exact XDK name is inferred from that behaviour; no signature was matched. The other runtime calls here are also not game code: `sprintf` 0x00125559, `vsprintf` 0x00125ECE, the `eh vector` iterators 0x00125D44 and 0x0012526B, `_purecall` 0x00125F25.

## Quirks of the original, kept

* **All a real controller's axes are built with `m_raw` 1, so nothing filters them.** `DeadZone` and `Saturation` from the file are stored in each handler and not applied, unless something unrecovered clears `m_raw`. With it set, `Apply` leaves `m_filtered` alone.
* `AtInputAxisHandler::Apply` negates `m_filtered` every time if bit 0 is set, so a raw one flips each call.
* `Setup`: a dead zone above the saturation sets the saturation to 95, including in the caller's copy. `Filter`: a value within 5 of the center is 0 whatever the dead zone.
* The percent constant is 0.01f, a little under 0.01, so a dead zone of 15 on a span of 10000 ends just below 1500.
* A controller with POVs and no axes has an axis input count and no second chains: a mapper with that POV id crashes in `BindAxis`. `AllocateInputs` tests `AxisCount()`, not the count.
* `AtInputRouter` has one free list, so a button binding can take a link from the axis pool, and the other way. With none left it writes through null.
* `BindAll` leaves `m_bindFunction` set. `BindAxis` passes 0 as the state.
* `AtInputDevice::Connected` counts those both started and acquired, and asking past the end gives null, which `BindAll` passes on, and crashes.
* `AtInputEventQueue`: `Allocate` keeps the lists' pointers; so does the destructor. `Flush` skips what the mask does not ask for and starts again from the first after each it drops.
* Every POV starts at two pi, by `SetValue`, so its "previous" is 0.
* `ClearHandlers` writes the eight POV angles to a global, 0x00301B08, every time.
* `AtInputControllerDatabase::m_unknown18` is passed to each `Read`, which ignores it. Nothing sets it. The owner is not kept, unlike the mapper database.
* `Read` updates the count of all inputs for `Buttons`, and the second count only for `Axes` and `POVs`. Each is in terms of what has been read so far, so the last word wins.
* `AtInputController::Start` calls slot 14 with `m_unknown1C`, a store of itself on the base and nothing on an abstract controller.
