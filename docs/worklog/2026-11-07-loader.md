# The Xbox database loader, `.XGG` and `.XKA` (subsystem `at/loader`)

Worktree branch, for the integrator. State: Semantic-tested. No byte match is claimed: the host compiler is not the original's. Names are inferred; the prefix `AtGrD3D` follows the original's own message at 0x0028B0BC, `AtGrD3DTm2Loader::vRead`, which shows how the graphics layer's classes were named.

## The question first: what do slots 7 and 3 reach, and are `.AGG` and `.AKA` dead?

**Slot 7 of the concrete mesh database is 0x001109E0, the `.XGG` reader; slot 3 of the concrete animation database is 0x00102970, the `.XKA` reader.** Both are recovered here, and the `.XKA` reader is complete: on a real `.XKA` it builds everything the text reader would, with nothing behind a seam.

The concrete classes are proved to be the only ones. The base mesh database's constructor 0x0002ADD0 has two callers, 0x001108B3 and 0x001110AA, which build the same class (vftable 0x0028A730, the second inline in its slot 8). The base animation database's constructor 0x0002A770 has one caller, 0x001028D3 (vftable 0x00289BB0). Each concrete class answers 1 from `HasBinaryForm` (0x001A2B40 in both tables). So the text readers run only if `Load` is given a mode other than 2.

`AtDatabaseLoader::Load` 0x0001ADC0 has five callers. The mode each passes:

| Caller | What | Mode |
| --- | --- | --- |
| 0x0001AAAA | nested loaders, in `LoadDatabases` | its own mode |
| 0x0008E290 | `DataXbox\UI\DirtyDsk\loader`, the dirty-disc screen | 0, always |
| 0x00013265, through 0x000118A4 | a Flash level's shapes (`Shape` in an `.AFD`) | 2 if the environment's flag at +0x224 is set, else 0 |
| 0x000BCEEB, through 0x000BC010 from 0x0017DFC1 and recursively 0x000BD30E | what 0x0017DE40 loads; not named here | `g_usePlatformBinary ? 2 : 0` (0x0017DF73) |
| 0x001B4206 | a slot of vftable 0x002950F0, beside the effects' words; not named here | `g_usePlatformBinary ? 2 : 0` (0x001B41B9) |

* `g_usePlatformBinary`, 0x002B9348, is 1 from the start and from the settings' constructor 0x00098131, and becomes 0 only through the App.ini or command-line word `DontUsePlatformBinary` (0x00098E1D; recovered in `src/gm/GmAppSettings.cpp`). The disc's `app.ini` holds only `DataFolder "DataXbox"`.
* The Flash flag is set by the word `PlatformSpecificFiles` in an `.AFE` (0x0002CE83, in the reader at 0x0002CD40). All 20 `.AFE` files on the disc have it. The `Shapes\*.AGD` they name list meshes.
* The dirty-disc `Loader.AGD`, loose on the disc, lists one `MaterialDatabase` and one `ImageDatabase`: no meshes or animations, so mode 0 sends nothing to a text reader.

On the disc, counted in every archive and loose (`tests/oracle/loader_cases.py`): 1,092 `.XGG` (442 distinct), 1,489 `.XKA` (565 distinct), and **no `.AGG`, `.AKA`, `.AGV`, `.AGP`, `.AKM`, `.AKW`, `.AGO` or `.AGH` at all**. Every name in every `.AGD` of every archive was resolved against its own archive: all 1,194 mesh names have an `.XGG` there and none an `.AGG`; all 1,658 animation names have an `.XKA` and none an `.AKA`.

**So the text readers `.AGG` and `.AKA` are dead on this disc as shipped, but not dead code**: they are reached by the development switch `DontUsePlatformBinary`, or by a Flash environment without `PlatformSpecificFiles`, and on this disc either would then open a file that is not there and stop in `AtReportFileError`. The same holds for `.AGV` and `.AGP`, which no `.AGD` lists.

One more binary form, for the record: the concrete font database's slots 4 and 5 (0x001A2B40, 0x00111630) are a binary form `.XGF`, but `AtFontDatabase::Load` never asks for it, and there is no `.XGF` on the disc. Not recovered.

## What the two formats are

From the readers, and checked on every real file by the oracle. Both start with 0x10 bytes that no reader looks at: on the disc, `HVSI`, the extension and a terminator, then two 16-bit numbers and a word (an `.XKA`: 2, 2; an `.XGG`: 2, 13). Then a table, then blocks, each read whole; the reader aligns to 4 after the table. Every pointer the readers make is a block's address plus a 32-bit offset from the table. Layouts: `AtXkaHeader`, `AtXkaAnimation` and `AtXggHeader` in `include/at/AtGrD3DDatabase.h`.

* `.XKA`: a table of 0x78 bytes; a scratch block (names of eight bytes, records of 0x60, read onto the token file's heap and freed) and a kept block (component lists and keys, owned by the database). Records are copied word for word into `AtAnimation`, their 32-bit runs cut to 16 bits. The keys get counts and pointers into the kept block, and flag 0x400, so that clearing does not free what they did not allocate. On the disc: 565 distinct files, up to 116 animations each, none empty.
* `.XGG`: a table of 0x58 bytes; a scratch block of records, a kept block on the mesh heap (aligned to 32 bytes at least while it is allocated), and a third block in memory for the graphics processor, absent in 42 of 442 files. Then items, kind by kind: vertex arrays (records of 0x3C), index arrays (8), streams (0x48), meshes (0x18, a name at 0x0C, with triangles, parts and material references beside). Each item reads its own part and moves the cursors on.

## Not recovered: the seam

`src/at/AtGrD3DUnrecovered.cpp` holds bodies for what the header declares and this work does not recover; each goes to one of seven functions in `src/at/AtGrD3DSeam.cpp`, which stop through `AtFatal` naming the original's address. A test supplies those seven instead. What the seam stands for:

* **The eight other kinds of database** the loader makes: textures 0x0010FFC0 (vftable 0x0028A6E0), materials 0x000F7790 (0x00289300), shaders 0x00110260 (0x0028A720), lights 0x001111B0 (0x0028A764), fonts 0x001115A0 (0x0028A774), images 0x00111BC0 (0x0028A794), vertex and pixel processes 0x00111E50, 0x001120B0 (0x0028A7AC, 0x0028A7BC). The classes exist with the original's sizes and the slots their bases require; every body stops, the constructor first. Their own work is making textures, surfaces and the like, which is Direct3D. Replacing one means deleting its bodies from `AtGrD3DUnrecovered.cpp`.
* **The items a mesh database makes**: vertex arrays (0x000EC890, reader 0x000EC8C0, which registers a vertex buffer, 0x00205DF0), index arrays (0x000F8010, 0x000F7EE0), streams (0x000EECA0, 0x000EE750) and meshes (0x00122460, 0x00122550, which finds its materials by name in the owner's tables and reads its parts at 0x0011B120). They derive from the recovered bases `AtVertexArray`, `AtIndexArray`, `AtMesh`.
* **Memory for the graphics processor**, 0x00205EA0 and 0x00205EE0.
* **The keys' own slots** but 1, 3, 6 and 14 to 18: allocation, interpolation, the readers of text keys, and slot 26, which turns a 16-bit translation into reals scaled by +0x40. So animations load, and cannot yet be sampled.

The owner the databases are loaded for, probably the graphics device, is not recovered beyond `AtGrD3DOwner`'s list of mesh databases at +0x3340 and of texture databases at +0x3338.

## What a real build does on real files

With the seam as it is, from a real `.AGD`, through `AtXboxFactory::NewDatabaseLoader` and `Load` with mode 2: the `.AGD` is read; lists of meshes, coordinate systems, animations, material lists and material animations are made by recovered code; the first list of any other kind with a count stops at its seam constructor. Of the 423 distinct `.AGD`: 412 stop at their `TextureDatabase` list and 8 at their `MaterialDatabase` list, while they are being read. Three get past the reading: `BOXREG.AGD` and `N5HATW.AGD` reach the `.XGG` reader, which reads the file's three blocks and stops at the memory for the graphics processor, or with no third block at the first mesh's constructor; `DCLSG1.AGD` reaches its coordinate systems, which need the owner's matrix device, slot 17, which stops: no concrete owner is recovered. Before any of it a real build needs an owner whose `m_animationDevice` is an `AtGrD3DAnimationDevice`; nothing recovered sets it.

With the seam supplied, as the host test and the oracle supply it, every real `.AGD` loads end to end: lists, arrays, every `.XGG` read to its items with every cursor checked, every `.XKA` read fully, then unloaded and destroyed.

## Oracle

`tests/oracle/oracle_loader.cpp`. What a green result does not show, first: the eight other kinds of database and the mesh's items are the seam's classes on both sides (the original's constructors are sent to them, with the original's own base constructor, destructor and base slots, so that the base's code on that side stays the original's). The items' readers are the harness's: they log the words at each cursor and the step since the last call, and move the first cursor by the size the original's step it, and no further. Text files an `.AGD` names open as empty text. So real files show that the loader, the mesh database and the animation database do the same, in the same order, with the same blocks, names and pointers into blocks, as far as those doubles: nothing of how an item reads its part, nothing drawn.

Cases: every distinct `.XKA` and `.XGG` (each read, cleared or read again over itself, the accessors at three indices, slot 8 on a fifth of them, cleared, destroyed; a seventh with reads pending and a seventh with the wait failing; fills of 0xCD and 0); every distinct `.AGD` from the archives, as the game asks, through each side's own loader, unloaded on every other one and destroyed; the loose dirty-disc `.AGD` at mode 0; written `.AGD` lists for each kind with 0, 1 and 2 names, nested loaders, everything at once; written `.XGG` and `.XKA` with and without a third block or a name space, at heap alignments 2, 5 and 6, cut short at the table's end and in each block, and missing; the keys' base under each combination of counts, an animation's record with signalling reals, the device's slots with and without memory, the factories with a heap, none and no memory, the binary file's ways of opening, the owner's list in each order of removal, the base's `Allocate` with counts the reader never passes; and, for the `.XKA`, `.XGG`, slot 8, `Allocate`, the device and a whole `.AGD`, each heap of this work missing in turn, and memory running out after each number of reads from one to seven, which crash or raise the same way on both sides. Seam calls log which object they are for, by the order the objects were made, so that an accessor giving the wrong element shows.

Not compared: bytes of a name after its terminator where it was copied from the stack. Reading a file in pieces of one byte: the table would be read short, and its rest is stack on each side.

`tests/native/test_loader.cpp` on x64, Release: passes. It supplies the seam, writes an `.XKA`, an `.XGG` and an `.AGD` in memory, and loads them through the real tokenizer, the factory's loader, the mesh and animation databases, and unloads.

## Quirks of the original, kept

* `AtGrD3DMeshDatabase` never sets +0x38, the stream count, in its constructor or `Clear`.
* `Clear` of a mesh database leaves `m_next`; the mesh database made by slot 8 (`m_more`, at +0x18 of the base) is forgotten by the base's `Clear` and freed by nothing.
* Slot 8 copies its group's name with `strcpy` into a buffer of twelve bytes of its frame. An eight-letter name has no terminator, so the copy runs on through the group's next fields and over the frame's exception record. Here the buffer is 0x20 bytes; only eight bytes of the name ever reach a name space. (Found by the oracle: the first version had twelve bytes, and the host's stack check stopped on `FEOPTION`.)
* The `.XGG` reader does not test the mesh heap for null, and raises the heap's allocation alignment to at least 32 bytes for the kept block only, then sets it back to the heap's own alignment, whatever it was before.
* A failed open or read is reported and reading goes on, with whatever the buffers held: in the game the report does not come back.
* Both readers align the file to 4 after the table, and the keys of an `.XKA` are marked 0x400 so that their `Clear` forgets, rather than frees, lists in the database's block; the database's `Clear` likewise forgets its component lists before the base's `Clear` would free them.
* The keys' base destructor resets the table to the base's, whose slots are the C library's pure-call handler, and then clears: with a count left it would call one. A concrete destructor always clears first.
* `AtIoBinaryFile::Open` looks at the top file system when `flags & 1`, unlike `AtIoFileRef`'s `& 0x21`, and closes a previous file without testing `m_fs`.
* The factories do not read `this`.

## Shared edits

* `include/at/AtAnimationDatabase.h`: `AtAnimationKeys` gains its constructor, destructor, `Clear` and `SetExternalName` overrides, `Init` and five counts at +0x14 to +0x24 (the base's own, vftable 0x00274C00); `AtAnimation` gains `ReadBinary`. **Slots 9 to 13 of `AtAnimationKeys` now take the count** they are called with (`ret 4` in the original): `Slot9()` became `Slot9(unsigned int count)`, names kept. I changed the overrides in `tests/native/test_agd.cpp` and `tests/oracle/oracle_agd.cpp` to match, one line each.
* `include/at/AtMeshDatabase.h`: `Allocate` 0x0002B0E0 declared (recovered in my file); `m_unknown18` is now a union with `AtMeshDatabase* m_more`, so that a pointer fits on x64. `src/at/AtMeshDatabase.cpp`: its two `m_unknown18 = 0;` became `m_more = 0;`, the same code on x86; so the `agd` suite's mutant `mesh ctor: 18` now names `m_more = 0;` (`tests/oracle/suites/agd.py`, one text changed).

## My mistakes

* Wrote the item seam classes first without their bases, so that `MeshAt` could only return a lie; then derived them properly.
* Took +0x24 of the mesh database for the list link and +0x4C for `m_more`; slot 8 and `MakeMeshes` showed +0x24 is the owner, +0x4C the link, and `m_more` the base's +0x18.
* Named the `.XGG` mesh cursors by position before reading the mesh reader; its arguments showed which block each is, and they were renamed.
* The first oracle ran the recovered base code of the seam classes on the original's side, so frees logged to the wrong side; it now runs the original's base constructor, destructor and base slots there.
* Read files a byte at a time in the oracle, which left the table as stack and hung on a garbage count.
* Left the base destructor test with counts set, which reached the pure-call handler on both sides.
