# Worklog: scenes, .ASN (2026-11-06)

For the integrator: this holds what belongs in docs/formats.md, docs/verification.md and docs/portability.md. State of this work: Semantic-tested. A host MATCH from `tools/verify.py` says nothing about the original compiler.

## What the format is

A scene: the file sets out how many coordinate systems and motion states it needs, then lists named nodes by class. This comes from the code and the text, not from a guess: the keyword table at 0x002B1990 (116 words), the original's own messages ("Atlas Scene: Error trying to cast a NULL node", "Atlas Kinematics ..."), and what the reader does with each word.

```
NameSpace "x"                 optional
RotTransCoordSys[n]           any order, each optional: counts only
ScaleCoordSys[n]
MotionState[n]
Node[n]                       the size of the name map. Required, and ends this part
ClassWord[count]              then any number of lists, one to a class
{
    ClassWord "name" RotTransCoordSys MotionState ScaleCoordSys
    {
        Position, Quaternion, BoundingSphere, Attach, ... the words of that class
    }
}
```

So `Node[n]` appears with two meanings: first, the total of names, and later, a list of plain nodes. Real files have both. The 652 distinct text cases use five classes only: Node, ModifierNode, ModelActor, JointedModelActor, ParticleSystemActor.

Words the base node reads: BoundingSphere, ActiveDistance (stored squared), Attach, AttachBase, AttachNodeToThisJoint, AttachNodeToThisBase, Position, OrthoNormalize, Quaternion, LookAt, LinearVelocity, AngularVelocity, CollisionEnable/Disable, BoundingGeometry, LineSegIntersectEnable/Disable, two MatAssignment words whose integer is thrown away, and four debug draw words that do nothing. The modifier node adds Modifier, ModificationEnable/Disable. Mesh, animation channels, emitters and so on belong to the classes not recovered.

## Recovered

85 functions, 7 vftables, in `src/at/AtCoordSys.cpp`, `AtScene.cpp`, `AtSceneNode.cpp`; 11,778 original bytes.

* `AtScene`: the loader 0x0003CD60, the reader 0x0003BCD0, constructor, destructors, `Clear`, the three "next" functions. Vftable 0x00275A44.
* `AtSceneNode`, base of every class (vftable 0x002765A0, 32 slots), and `AtSceneModifierNode` (0x00276C68): the read path, copy, start from a description, clear.
* `AtCoordSys`, `AtRotTransCoordSys`, `AtScaleCoordSys`, `AtCoordSysDatabase` (0x00274AE8, 0x00273100, 0x00274B08, 0x00273120). 0x00026920 is `AtCoordSysDatabase::Allocate`, shared with the AKC loader.
* `AtSceneModifierSet`'s five removal functions, the owner's lookups, sphere and motion state helpers, `AtQuaternion::Read`.
* 0x00011000, shared with a later format: `AtConstructEach`, 48 bytes. The original takes a thiscall pointer; this takes a plain one, since `__thiscall` does not exist on a 64-bit or GCC build. Its callers pass a function that constructs.

## Not recovered

The closure of the loader, with vftables followed, is 522 functions and 72,639 bytes including the C library and exception funclets, far past the 40 or so this round was meant for. What was left out:

* **Nine classes of node**: ModelActor (vftable 0x00276620), JointedModelActor (0x002766D0), ParticleSystemActor (0x002767C0), GroupActor (0x00276870), LodGroupActor (0x00276920), SwitchGroupActor (0x002769D0), WaterActor (0x00276A80), LensFlareActor (0x00276B30), SoundNode (0x00276BE0), and their base at 0x00276FA8 (reader 0x00056500, 1240 bytes). `AtScene` reaches them through `AtSceneActorsSize/Construct/Destroy`, `AtSceneActorSharedCoordSys` and `AtSceneActorJoints`, which `src/at/AtSceneActorsHost.cpp` answers with a diagnostic. **So in a real build today, any scene holding one of these stops there**, and nearly every real file holds one.
* `AtSceneNode` slots 12 to 31 and `AtSceneModifierNode` slot 12: moving and testing nodes in a running game. Each stops with a diagnostic. Slot 12 of the base calls 0x0004F620, slot 14 calls the collision code.
* 0x0003CE10, a sibling of `Read` that builds a scene from a table of counts, not from text. Called once, from 0x0014F8DE.
* The matrix functions. The original calls them through a table at 0x002C60C8 onward, set up at about 0x000EC670 in the graphics layer. `g_atMatrix` holds the ten this code uses; each stops with a diagnostic until set. What each does is inferred from its arguments only.
* The rest of the modifier set class, 0x00039E90-0x0003AFFF, which makes the links this code removes. The ASG, ASI and AST loaders sit in that range.

## Oracle

`python -I tools/oracle_run.py --suite asn`. See the end of this file for the result on the final source.

The nine classes above are doubles on both sides. On the original's side the double is its base class's own code with the constructors redirected and a harness vftable, so the original's array iteration, its eh iterators, its vector deleters and its actor slots 0x00055B80, 0x00055BD0, 0x00055BE0 and 0x00055C00 all run. Both sides share one function that takes the arguments of words those classes own, so **those words are consumed and not compared**: Mesh, channels, emitters, the coordinate system databases. Everything the scene, the base node and the coordinate systems do with a real file is compared. `Scale` reaches the real scale coordinate system. The harness gives every jointed actor a joint map holding all names in the file, as the real class fills it from a file not read here, and adds a fallback map of stand-in targets, so attachments to things in other files succeed.

Compared after each step: every word of each node, coordinate system and motion state, pointers by what they lead to; the name maps; group membership; every matrix; a running hash and log of calls to the device, the matrix table, the heap and the file; all messages. Allocations are filled with 0xCD, and two cases with other fills.

The original's matrix table is pointed at logging functions, on both sides.

Cases: all 652 distinct `.ASN` text files, each loaded twice, cleared twice, destroyed. 24 file heads; 12 class words with 10 list shapes each; header words; running out of each array; 48 body words on 4 classes, with and without a coordinate system; attachments inside one file; no heap, per class; no memory, per class, through a wrapper of the heap stack; a file that will not open. Directly: 20 seeds of 2,000 random operations on a tree of coordinate systems; databases of 8 shapes; copies; descriptions; modifier sets in 64 shapes.

### Limits and things not run

* A file ending inside a node, or before `Node`, reports for ever on both sides, because the report comes back in the harness and not in the game. A harness counter crashes deliberately after 40 reports in a load, inside the guard, so those are compared up to there. After any crash, only logs and messages are compared.
* Attaching a node to itself recurses for ever in both, past what the guard catches. Not run. Cycles of coordinate systems likewise.
* A name that is not a string where one is required leaves an uninitialised stack buffer in use on both sides, as in the material database. Not run.
* Node map values that lead nowhere known (past the end of an array, or left behind when a node was attached twice, or a list given twice) are compared only as "unknown on both sides", since they are not read.
* `Next` with no file name: the tokenizer's report starts from an uninitialised buffer in the original (docs/verification.md), so there the log shows a report happened, not its text.
* The recovered array destructors are not the original's vector deleters. Recovered source writes out the count ahead of an array by hand (`src/at/AtSceneArray.h`), because a heap here may answer null and `new[]` is assumed not to. The original's are run and compared by their effects; they have no recovered twin to call. `??_G` symbols are recorded for them, and the vftable check maps slot to address.
* Slot 0 `ScaleFactor` is compared as stored to a float.

## Quirks of the original worth keeping

* `AddScene` tests the name space for null only, while `FindNode` also treats an empty one as none. So `NameSpace ""` files a scene under a space with an empty name, where a lookup with an empty name never finds it.
* `NextRotTrans`, `NextScale` and `NextMotionState` report running out, then return the element past the end regardless. With a count of 0 that is a null array plus 0.
* `AsJointed` reports a null or wrong class and hands the pointer back. With a report that does not return, the checks after it are dead code; they are kept.
* A list word given twice reports, then allocates again, leaking the first array and leaving its names in the map. Clearing then frees only the second.
* A node attached to a second parent is not removed from the first's list. The first keeps a stale pointer, and clearing removes it only from the second.
* `AtScaleCoordSys::Invalidate` is empty, so an invalidate stops at a scale coordinate system, unlike the base's.
* `Visit` (slot 7) only asks children to do the same; nothing happens anywhere in it.
* `Detach` on a scale coordinate system invalidates the child; attach marks from the parent down.
* `AttachToJoint` clears bit 0x00100000 of the parent's flags, for a reason not seen here.
* ModifierNode's `Clear` removes itself from kind 0 of its set, and the base's from kinds 1 and 3. Nothing clears kind 2 here.

## Portability notes

* `AtSceneActorSharedCoordSys` (+0x90) and `AtSceneActorJoints` (+0xA0) are seams because the base class reads fields of classes derived from it, by offset. They must become proper members when the actors are recovered.
* An array's count ahead of it is one `size_t`, so 4 bytes on the Xbox and 8 on x64, with the elements still aligned.
* `AtNameTableOwner` (folded in at integration; this notes its name then, `AtSceneOwner`)'s padding preserves 32-bit offsets on the Xbox only; on x64 members keep their names and order, and nothing depends on the offsets.

## Mistakes along the way

* My first reading of `AtSceneNode::Read` had the slots at the end of the header and the body the wrong way round: slot 6 runs after the header, slot 2 after the body. Caught on rereading the disassembly, before anything ran.
* I first wrote the double's constructor to set +0x80, +0x90 and +0xA0 on every class. The sound node is 0x70 bytes and a model 0xA0, so that wrote past the object, into the next element or the heap. Shown by heap corruption in the harness.
* The first harness let the coordinate system tree form cycles, which overflowed the stack on both sides; the deleter test freed the wrong address; and I used the recovered tokenizer on the original's side, whose reports then landed in the other side's log.
* **Hollow text cases**, found only by the mutants. 30 survived the first run of 413. Written text used integers such as `LookAt 1 2 3 ...` where the reader expects reals, so the values never reached the matrices, and both sides agreed on reports and zeroes. They are now decimals, with one integer case kept.
* The rest of those 30 were real gaps, each now closed by a direct test: fields overwritten by what always came next (a reset followed by new matrices, `FinishBody` after `BoundingSphere`, `Reset` after a release, `Load` setting the owner before `Read`); heap setters called with the value already there; lists never more than one long; a scene never destroyed while loaded; the order of destroying arrays, which nothing logged. That order is now read from the free list of a modifier set and from a spy parent.
* The second run was 411/412. The survivor was mine again: the sources of class 1 and class 13 had no coordinate system, so that test could not reach the class check. Both ends now have one, with a mutant for each.
* One was equivalent and is dropped, with the reason beside the list: removing `file.Close()` in `Load`, since the destructor does the same.
