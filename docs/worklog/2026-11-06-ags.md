## Findings

* `.AGS` holds shaders, now established: the file's top word is `Shader[n]`; the keyword table at 0x002B0CC0 has `Shader`, `TextureStage`, `StagedShaderComponent`; the messages say "used by shader"; and a database joins `AtMaterialOwner` at +0xB4 or +0xCC, which is what `FindShader` searches.
* 0x00025EF0 is a sibling of `AddMaterials`, as suspected: same code, on the shader tables.
* The owner has two more groups, +0x36C vertex processes and +0x384 pixel processes. Only the programmable reader reads them here.
* The disc's 267 text cases use only staged components: 485 shaders, 647 staged, no programmable one. `.AGS` has a programmable path that real files in these cases never reach, so it rests on written text alone.

## Quirks of the original, kept unless stated

* **Not kept: the pixel process message overruns its buffer.** 0x00045070 builds name plus message, up to 72 bytes, in a buffer with 52 before its saved registers, and the text goes over them. In the game the report does not come back, so it does no harm. If it does come back the original crashes in whatever follows. The recovered buffer has room. This is the one deliberate difference. The oracle stops the original at the report and compares everything up to it: message, log, fields.
* `m_transforms` holds eight and is not bounds checked. A ninth goes over `m_transformCount`, and what follows lands where that value says. Kept on the x86 layout and compared with values that stay in the object. On x64 the two remain adjacent `unsigned int`s; a write past the array is still undefined in C++. For docs/portability.md.
* `TextureStage[n]` over eight reports and, if that returns, reads on over `m_vertexProcesses`, `m_pixelProcess` and the next element. Compared, with a ninth stage that has no texture, since one with a texture would later be freed as a list.
* Read notes transforms only of staged components. 0x00037680 and 0x000376F0 are called from the graphics layer.
* `CoordViewToWorldTransform` clears the other transforms, and they do not clear it.
* `AtStagedShaderComponent::Clear` leaves the combine op. `AtProgShaderComponent::Clear` leaves the combine op and the stages. The database clears its map twice.
* `ModulateOp SelectModulatedOutput` is refused, though `AlphaSource` takes it.
* `AtShaderDatabase::s_heap` is only read by the graphics layer. Two parameters are not used: `AtShader::Read`'s database, `AtStagedShaderComponent::Read`'s index.
* The array cookie is written out by hand in `NewArray` and `DeleteArray`, since a modern `new[]` assumes it does not return null and the original goes on after a null, raising -4. Sizes wrap at 32 bits, as there. On x64 the cookie takes eight bytes, for alignment, of which four are used.

## Mistakes and fixes

* My first version of two written texts did not balance, one with a `Border` short of its numbers. The original and the source both spun at the end of the data, and the run timed out at 900 seconds. I found them by reading, gave them closing braces, and left the end of the data to the direct cases.
* A crash in the original's tokenizer code on `PixelProcess "XGone"` looked like a harness fault. It was the original's buffer overrun above, found from the frame size.
* My test of counts with no arrays gave a staged count to `Read`, which walks it. The original crashed, correctly.
* Eight mutants survived the first full run. Two are equivalent and dropped. Six were real gaps: no duplicate name followed by an error in the shader; no direct `Clear` with a list; no count with its top bit set, twice; no `FlipFaceCulling` before `DisableColorWrites` in a programmable component; staged components were missing from the one-heap-at-a-time cases.
* A Python edit through a shell heredoc silently failed its first try, since doubled backslashes did not survive; caught by an assertion in the script, before anything changed.
