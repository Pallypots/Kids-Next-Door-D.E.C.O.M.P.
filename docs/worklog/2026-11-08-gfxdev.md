# The graphics device: its abstract layers, construction, member slots (2026-11-08)

Subsystem `at/gfxdev`, worktree branch, for the integrator. This file holds what belongs in docs/verification.md and docs/portability.md. State of everything recorded here: Semantic-tested. A host MATCH from `tools/verify.py` says nothing about the original compiler.

## What a real build now does

**`AtMaterialOwner::MatrixDevice()` no longer stops on the real owner.** The owner a game's loader is given is the concrete graphics device, `AtGraphicsDeviceXbox` (vftable 0x00289208, constructor 0x000F1FA0, 0x305C0 bytes), now recovered: its slot 17 (0x000EF2E0) returns its `AtMatrixDeviceXbox` member at +0x3E40. AtMaterialOwner's own slot 17 is pure in the original (0x00125F25) and still stops with a diagnostic, as a pure call does; only a harness owner reaches it.

**A real `.AKC` load can start from the real owner, with one condition: the texture work's classes.** The device holds three members of classes that work recovers (the concrete texture database, vftable 0x0028A6E0, and two kinds of texture, 0x00289768 and 0x00289700; 19 members in all). Here they are storage of their size, made and destroyed through six seams (`AtGfxConstructTextureA` and so on, include/at/AtGraphicsDevice.h), which `src/at/AtGraphicsDeviceHost.cpp` defines to stop. **So on this branch alone, constructing a real device stops at its first member, the texture at +0x3B0.** Once the texture work's classes are merged, the device constructs and a load runs through it: shown on x86 by `oracle_gfxdev`, which supplies the six seams with the original's own constructors (0x000FCEE0, 0x000FC630, 0x0010FFC0) and then reads **all 544 distinct `.AKC` files** through each device's slot 17, the original device's own slot on one side, the recovered device on the other: 2,195 coordinate systems, 6,830 matrices, every world matrix and pool matrix the same bit for bit, the same 14,228 calls to the heaps. And on x64 by `test_gfxdev <text cases>`, whose stand-ins for the six seams only clear the storage: the same 544 files, 2,195 coordinate systems, 6,830 matrices, through `AtMaterialOwner::MatrixDevice()` on the recovered device, no world matrix not finite.

What the integrator does at merge, to make that real: use the texture work's class for each of `AtGfxTextureASlot` (0x50 bytes, constructor 0x000FCEE0, destructor 0x000FD8C0), `AtGfxTexture2DSlot` (0x34, 0x000FC630, 0x000FCCC0) and `AtGfxTextureDatabaseSlot` (0x58, 0x0010FFC0, 0x001101D0) as the member type, delete the three wrappers and the six seams in `src/at/AtGraphicsDeviceHost.cpp`, and in `tests/oracle/oracle_gfxdev.cpp` and `tests/native/test_gfxdev.cpp` drop the six stand-ins. On x64 the storage is the x86 size, which the real classes will not be: another reason to replace it rather than keep it.

**Tearing a device down still stops.** The destructor 0x000F5290 calls slot 1 (Release, 0x000F2750) first, which releases Direct3D objects and is not recovered; written (draft, not compared) and mapped in `[symbols]`, not recorded. A game also needs the device's maker, 0x000EBE90 (slot 25 of the class at vftable 0x00288B88), which stores itself at +0x3A8; not recovered.

## One class: AtSceneDevice, AtMaterialOwner, and the class in 0x00027B70-0x0002AC10

Established, and folded: `AtSceneDevice` is now `typedef AtMaterialOwner AtSceneDevice;` (include/at/AtScene.h, include/at/AtNameTableOwner.h). Evidence:

* **One constructor builds every table.** 0x00026190 (AtMaterialOwner's, vftable 0x00273030) constructs the group and name space database at each of +0x3C ... +0x2E8 and the six plain groups +0x30C ... +0x384. Every table the scene code reads through `AtSceneDevice` is one of these, at the same offset with the same type. That constructor has one caller, 0x000F1FBF in the graphics device's constructor, and the device's base vftable is used only by it and its destructor 0x000266F0: so any object with these tables is a graphics device.
* **The finders are one family.** The two the scene calls on its device, FindMesh 0x000283F0 (+0xF0/+0x108) and FindMatAssignment 0x00028430 (+0x1A4/+0x1BC), are byte for byte the same code as `AtMaterialOwner::FindMaterial` 0x00027EF0 (+0x78/+0x90), in the same cluster, between AtMaterialOwner's methods. That cluster, 0x00027B70-0x0002AC10, is the loaders of the .AGN/.AGA/.AGH/.AGI/.AGF/.AKA/.AGL files and those finders: the "class" there is AtMaterialOwner, every function in it taking the owner as `this` or as its argument.
* **The same slot 17.** Both views call slot 17 for the matrix device; the concrete device's is 0x000EF2E0.

The scene's four names that differed are renamed to AtMaterialOwner's (same offsets): `m_coordSysDatabases` to `m_coordSystems`, `m_mirrorDatabases` to `m_mirrors`, `m_weightDatabases` to `m_weights`, `m_animationDatabases` to `m_animations`.

**The base under AtMaterialOwner** is another class: `AtDisplayDevice`, vftable 0x00274AD4 (five slots), constructor 0x00032200, 0x34 bytes: a display mode (`AtDisplayMode`, 0x24 bytes: width, height, an AtPixelFormat, two words; 0x0008DBA0 fills one with 640, 480 and a 32-bit format and hands it to the device's slot 4) and a few words, among them `m_noTextures` at +0x30. The device's slots 23 and 24 hand on the mode's width and height.

**Also found: `AtMatrixDeviceItemB` is the concrete Xbox index array.** Its vftable 0x00289358 has base 0x00274D48, whose constructor 0x00037370 clears exactly `AtIndexArray`'s +0x0C and +0x14, and base-base 0x002762B8 (0x00044800) its +0x04 to +0x0B; 0x00274D48 sits beside `AtIndexArray::Read` 0x000373C0. So the matrix device's slot 3 makes index arrays (and slot 2, by the same reasoning, probably vertex arrays: 0x64 bytes, vftable 0x00288CF8, another root). I recovered the constructor chain as `AtGeometryArray` (new base of `AtIndexArray`) and `AtIndexArrayXbox`. **`AtMatrixDeviceItemB` should be folded into `AtIndexArrayXbox`**; I did not, since matdev's harness overrides its slots under other names and signatures. Two names for one class remain until then.

## Quirks kept

* **The context's shared words.** ResetBase (0x00058BD0) points +0x294C at three words at 0x002C9BF8 shared by every context and clears them: resetting any context clears every context's.
* **AtMaterialOwner's Reset order** is not the members' order: the plain groups from the last, the coordinate systems after the mirrors; then the pairs from the images down, the table at +0x12C before the lights, the light animations between the lights and the meshes. The order of frees is compared.
* The name space databases are cleared through their vftables, the groups only forgotten (their maps keep pointing at them).
* `m_animationDevice` (+0x38) is not set by the constructor. Reset clears `m_noTextures` and the three bytes after it as one word.
* The state cache's Reset clears its block pointer without freeing it; only the destructor frees.
* The context's destructor leaves its device's list only if +0x10 is nonzero, whether it is in the list or not; it calls the base's Reset (not its own slot 2) before its own words, and the base's destructor resets again.
* The resource root stores +0x30 twice. Init leaves +0x3DFC, +0x3324-0x332B, the gap +0x13190-0x2CFDF and others; the constructor leaves m_animationDevice.
* `AtGfxLessAt10` is `a < b` on the floats at +0x10: 0 for equal and for NaNs.

## Oracle

`python -I tools/oracle_run.py --suite gfxdev`. Each part makes one object of the original's (its own constructor on fresh memory) and one recovered on memory filled alike (0xA5), drives both the same way and compares every word. Words may differ only as: a recovered vftable against the original's address for it (a fixed map, from an object of each recovered class); a pointer into the block against the same offset in the other; the shared words and the ordering function against the recovered ones. Each freed block is logged by its allocation's number, so which block is freed when is compared.

Cases: the display mode's constructor and Clear on garbage; the display device's constructor, Reset through its slot, destructor, deleting destructor; the owner's constructor, then Reset, destructor and deleting destructor on an owner with all twelve name space databases holding pools and garbage in every group and word; **the whole device's constructor, all 0x305C0 bytes**, and the shared words; slots 13-18, 20, 21, 23-25 through the base pointer on each side's own vftable, with the creator and mode set three ways; UnlinkContext on five lists, each of five contexts taken out; the context's destructor on garbage, first in its device's list, in the middle, and in it but not marked; the state cache's constructor, Reset, ResetState, destructor with and without its block; the draw lists' Clear through slot 2 and destructor, for each of eight masks of blocks; the block lists' Clear and destructor and the pair's Clear for each of 32 masks; the ordering on all pairs of fourteen values, signed zeros, infinities and NaNs among them; and the 544 `.AKC` files as above.

Result on 2026-11-19: `NO DIFFERENCE OBSERVED: 213539 comparisons, 0 differences`, with `.AKC files read through each device's slot 17, the original's and the recovered: 544 files, 2195 coordinate systems, 6830 matrices, 14228 calls logged`; entries reached 53 / 53; `--mutate` fails as it must. **159/159 mutants detected**, positive control passes, none left out. The first run had 158/159: "context base destructor: no reset" survived, because its one caller resets the base just before; a case running the base's destructor 0x00059540 alone on garbage closed it.

After the shared edits, `--suite all --no-mutants` shows no difference in any of the 40 suites (which also checks every mutant text still occurs once, the actor and agn suites' changed texts among them; their mutants were not rerun). `verify.py` over the whole project: no MISSING, no UNRESOLVED; over the 53: 15 MATCH, 38 SIZE; vftables 0x00274AD4 and 0x00289208 MATCH.

What a green result does not show:

* **The texture work's members** are made on both sides by the original's code: compared, but they say nothing about recovered code.
* **The device's destructor, Release and the member destructors behind seams** are not run.
* The `.AKC` part uses the recovered matrix functions on both sides; it compares the device each owner's slot 17 hands out, its makers and its pool, not the matrix arithmetic (matdev's suite does that).
* Heap fill only shows a missing store as a word left at 0xA5; a store of a value that happens to be 0xA5A5A5A5 would not show.

## Portability

* The device is 0x305C0 bytes on x86 and larger on x64 (pointers, vftables); nothing in data depends on its layout. The texture storage wrappers are the x86 sizes, so on x64 only a stand-in that writes nothing beyond them may be used: replace them at merge.
* `AtGfxLessAt10` compares floats directly; NaN gives 0, as on x87.

## Mistakes of mine

* I first sized the resource at 0x4C and the gap after the 128 resources from a wrong end (0x30038 for 0x2F838); the static asserts caught both.
* The oracle first numbered freed blocks with a std::map, used by operator new before static constructors ran: it crashed at start. Numbers now live in a header before each block.
* The oracle first counted allocations made outside a recorded call on side 0 only, so every freed block's number differed; only recorded allocations are numbered now.
* A heredoc ate backslashes in a patch, as the notes warn; patches since are Python files written with the write tool.
