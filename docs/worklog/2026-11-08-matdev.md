# The matrix device, its pool, and the last five matrix-table slots (2026-11-08)

Subsystem `at/matdev`, worktree branch, for the integrator. This file holds what belongs in docs/verification.md and docs/portability.md. State of everything here: Semantic-tested. A host MATCH from `tools/verify.py` says nothing about the original compiler.

## What a real build now does on real files

**The device is real.** What `AtCoordSysDatabase` takes its matrices from is now the recovered `AtMatrixDeviceXbox`, and its pool `AtMatrixPoolXbox`, the classes the original's code makes, with the original's vftable layouts (both vftables MATCH in `verify.py`). On the disc's **544 distinct `.AKC` files**, read by the host's `AtCoordSysDatabase::Read` with the recovered device and the recovered matrix functions, every file loads to the end: 2,195 coordinate systems, 6,830 matrices of 64 bytes from the pool, every world matrix finite after `UpdateWorld` and `UpdateInverse`. That is the x64 host build (`test_matdev <text cases>`). On x86, `oracle_matdev` does the same twice, once with the original's device and pool (its own code, through its own vftables) and the original's matrix functions, once with the recovered ones: every matrix, every transformed point and every world rotation as a quaternion the same, bit for bit, and the same 28,074 calls to the heap, the heap stack and the reports, in the same order.

**What still stops a real `.AKC` load in a real build is the owner's slot 17, not the device.** The game reaches `AtCoordSysDatabase::Load` from 0x0001A4B0 (`src/at/AtDatabaseLoader.cpp`), which asks `owner->MatrixDevice()`. The owner is the graphics device: vftable 0x00289208, constructor 0x000F1FA0, which derives from `AtMaterialOwner` (its constructor 0x00026190 sets the base vftable 0x00273030, where slot 17 is pure). Its slot 17, 0x000EF2E0, is `lea eax, [ecx + 0x3E40]`: the matrix device is a member at +0x3E40, made in place at 0x000F2131 by the base's constructor 0x0010F800 and then the vftable 0x00288B48. The graphics device is not recovered (26 slots, a 719-byte constructor building texture, shader and light tables), so `AtMaterialOwner::MatrixDevice()` still stops with its diagnostic, and so a game's load stops there. Replacing that is a matter of a class for the graphics device with an `AtMatrixDeviceXbox` at +0x3E40 and slot 17 returning its address; I did not invent one.

A real build must also set both heaps, as the startup 0x000C7CA0 does (not recovered): `AtMatrixDeviceXbox::SetHeap` (0x000F7BD0) and `AtMatrixPoolXbox::SetHeap` (0x000F5FC0), each from its own field of the startup's table or the default heap. The pool's heap must be a real `AtHeap`: `Reserve` writes its `m_allocShift` and does not check for null.

**`tests/native/test_actor.cpp`** (the actor subsystem's; not changed): its `Matrices` device hands out 12-byte `Mat`s and its `set_tables()` installs ten matrix stand-ins in `g_atMatrix`. To load the 652 `.ASN` texts with real matrices it would need: its `Device::MatrixDevice()` to return an `AtMatrixDeviceXbox` instead of `Matrices`; `AtMatrixDeviceXbox::SetHeap` given any non-null value and `AtMatrixPoolXbox::SetHeap` given an `AtHeap` (zeroed storage of `sizeof(AtHeap)` will do: the host's operator new does not read it); the ten `g_atMatrix` assignments removed, and with them `Mat`, `Pool` and `Matrices`. Its own checks of a matrix's first three floats as a position would then have to read elements 12-14. Beyond matrices, a real `.ASN` load still needs what the particle and actor worklogs list.

## Quirks kept

* **The pool asks for 64-byte alignment by a heap field.** `Reserve` sets its heap's `m_allocShift` to the larger of `m_alignShift` and 6, allocates, and then sets `m_allocShift` back to `m_alignShift`, not to what it was. The device's single matrices get no such request. The original's SSE matrix functions use `movaps`, so a pool matrix must be at least 16-aligned in the original: the oracle's first run faulted inside the original's `Copy` on 8-byte aligned blocks from `calloc`, and its heap double now aligns to 64.
* **`Reserve` keeps the count before allocating**, so after a failure the count stays and the block is null. Its size is `count << 6` in 32 bits, and its construction loop counts down from `count - 1` as a signed number: a count of 0x80000001 or more allocates the wrapped size and constructs nothing; 0x80000000 constructs 2^31 matrices into a zero-byte block. Its heap is not checked for null, where the device's makers report it (AtRaise -2) and go on, pushing null.
* **Slots 0-3 dispatch again**, through the vftable to 8-11: a derived class could replace the makers alone. 4-7 do not.
* **The pool's slot 0 is the deleting destructor**, pure in the base; the base's vftable 0x002892CC has six pure slots, the device's base 0x0028A658 sixteen. The header keeps the pool's slot 0 as `Slot0()` because every harness pool overrides it by that name; the recovered `Slot0()` destroys and frees, as the original's does with the flag 1 that its one caller found, `FreePool`, passes. Device slots 6-15 are declared on the concrete class only, since no harness device has them; a caller through `AtMatrixDevice*` would need them moved to the base.
* **The rotations' 3x3 is three rows of four floats on the stack, the fourth of each never written**: neither product reads it. Both products sum three exact products in a register and round once: the pre product's rows 0 and 1 add the first and third and then the second, its row 2 the first and second and then the third; the post product's columns likewise. The pre product multiplies all four columns of rows 0-2, the post product columns 0-2 of all four rows, leaving the fourth column.
* **`GetRotation` does not normalise.** It takes the trace way only for a trace above 0 (not a NaN). Of the three diagonal ways, the x way subtracts the sum of the other two diagonal elements as the original spilled it, rounded to float; the y and z ways take that sum afresh in a register. Ties go to the earlier axis. It writes as it goes and reads the matrix after writing, which shows when the quaternion is the matrix's first row: compared.

## Oracle

`python -I tools/oracle_run.py --suite matdev`. Three parts.

* The device and pool, slot by slot: one object of the original's (its own memory and vftable, so its own code runs) and one recovered, driven by the same C++ calls through the same pointer type. The original's operator new and delete, heap push and pop and `AtRaise` are redirected to doubles that log into the same log as the recovered side's; each allocation logs its size and the pool heap's allocation shift at that moment. Heaps set by the original's own setters on its side. Cases: both heaps, no device heap, allocation failing, and both again; matrices through slots 0 and 8, pools through 1 and 9; `Reserve` on ten counts, including 0, 37, wrapping counts and one that fails, with six alignment shifts below, at and above 6, starting from a garbage allocation shift; every slot of the pool on five indices including 0xFFFFFFFF; `Clear`; freeing through slots 5 and 13; frees of null and of harness items for slots 6, 7, 14, 15, logging the flag their destructor gets; the original's forwarders for slots 2 and 3 run on the recovered device, reaching its stopping slots 10 and 11 by the message's hash, as the recovered forwarders do; the complete destructor run directly and the base's vftable left behind. Fresh memory is filled with 0xA5, so a missing store shows.
* The five slots and two helpers: the original's 0x000EC2B0 fills a table; each slot must hold the function read for it and is called through that slot. 200,000 rounds of ordinary and edge values, 50,000 with infinities and NaNs, 50,000 with signalling NaNs. Angles: anything, multiples of pi/8, and -7 to 7. Matrices: rigid, cancelling (three values and their negatives, so a sum's order shows), random. For `GetRotation`, also rotations near 180 degrees about each axis, and diagonals with ties and zero traces. The products also with their rows inside the matrix itself, and `GetRotation` writing into the matrix's first row, so that what is read after writing shows.
* The 544 `.AKC` files, as above.

Result on 2026-11-08: `NO DIFFERENCE OBSERVED: 44531373 comparisons, 0 differences`, with `.AKC files read with the original's device and matrix functions and with the recovered ones: 544 files, 2195 coordinate systems, 6830 matrices, 28074 calls logged`; entries reached 29 / 29; `--mutate` fails as it must. Mutants: see the summary line below.

**96/96 mutants detected**, positive control passes; none left out. Eight GetRotation matrices are fixed cases rather than random: the grouping of the y and z ways' radicand (`a - (b + c)` against `(a - b) - c`) differs by an ulp of a double only when `b + c` is inexact, and that reaches a float only at a rounding midpoint, so 300,000 random rounds did not show it. `analysis-local/scratch/matdev/search_rotation.py` builds them: a huge negative x diagonal so the sum is inexact, and the pair `w` is taken from solved so the product straddles a float midpoint. On each, the original agrees with the recovered grouping.

`verify.py --only` over the 29 and the two vftables: functions 10 MATCH, 1 MISMATCH, 18 SIZE; vftables 2 MATCH. None MISSING or UNRESOLVED.

What a green result does not show:

* **The rotations' sines and cosines** are the host's `AtSin` and `AtCos` (src/at/AtMathHost.cpp), which on x86 are the same `fsin` and `fcos`, but go through a double before the float: the original stores the x87's 64-bit result to float directly. The two can differ only where the 64-bit result lies within half a double's ulp of a float's rounding midpoint, about one in 2^29; none showed. On x64 they are the C library's `sin` and `cos`, so the x64 host test checks the rotations by structure and the oracle alone by bits.
* **Device slots 10 and 11** are not compared against the original: its objects are graphics objects not recovered. Only that slots 2 and 3 reach them is.
* The items freed by slots 6, 7, 14 and 15 are harness classes; that slot 2 of the first and slot 1 of the second are deleting destructors is read from their vftables (0x001105C0, 0x00110620), not run.
* Alignment: in the oracle every block is 64-aligned on both sides. The host build's operator new does not see the heap's allocation shift.
* NaN sign and payload from arithmetic are not claimed (counted apart, as in the matrix suite).

## Portability

* `src/at/AtMatrixAxis.cpp` turns off contraction as `src/at/AtMatrix.cpp` does; the same GCC note applies (`-ffp-contract=off`).
* The pool's block is `count << 6` in 32-bit unsigned on any host, as the original's: on x64 the wrap is kept, not widened.
* A matrix is 64 bytes on every host; nothing here holds a pointer in the game's layout. The objects themselves (`AtMatrixPoolXbox` 0xC bytes on x86) grow with pointers on x64, which nothing in the data depends on.
