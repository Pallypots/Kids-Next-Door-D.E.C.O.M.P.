## What the format is

From the code and the 20 real files, one per user interface archive (`DataXbox/UI/Xbox/*.JAM`):

```
.AFD    Loader { Level "name"  Sprite "name"  Shape "name"  Text "name"  Script "name"  [Sound "name"] }
        Each word loads at once, in the file's order: Level is name.AFL; Sprite is Sprites\name.AFP and the frames; Shape is Shapes\name.AFH and the .AGD it names; Text and Script are not recovered.
        Sound is read and dropped. Any other word is reported and the loop goes on.
.AFP    NameSpace "s"  Sprites[n] { SpriteDef { index FrameRefs[n] { frame,"name" | frame; | from:to | frame*times ... } } ... }
.AFH    NameSpace "s"  GraphicsDatabaseLoader "agd"  Shape[ n ] { Shape index { Rectangle r r r r  MeshAssignment i "name" } ... }
.XFF    binary, little-endian. 16 bytes: "HVSIXFF\0", then 8 bytes not read here (01 00 01 00, and the file's size).
        16 bytes: u16 frames, u16 offset of the data, u32 size of the data, u16 places, u16 actions, u16 removes, u16 sounds.
        The data, at that offset: per frame, u32 index, u8 places, u8 actions, u8 removes, u8 sounds; then that frame's tags, removes first, then places, actions, sounds.
        An action, remove or sound is a u32. A place is 0x18 bytes: u8, u8 (not read), u8, u8, u16, u16, u32, then three u32 offsets, counted from the end of the record, of a name, a 6-word transform and an 8-byte color
        (4 bytes, then 4 scaled by 1/255); 0 means none. Every tag of a kind comes from one run of objects for the whole file, in file order.
.AFF    the text form of .XFF, "Frames[n] { FrameDef ... }": read when the environment's +0x1F4 is 0. No .AFF is on the disc, and its frame reader is not recovered.
```

Which of .XFF and .AFF is read is decided by the .AFE environment (+0x1F4): the 20 .AFE files all have the word `PlatformSpecificFiles`, and all 20 archives hold an .XFF and no .AFF. The name of that field is a guess from the word.

## In a real build

`AtFlashLevel::ReadDefinition` on a real .AFD: the .AFL loads, the sprites load (.AFP and .XFF), then the shapes: they read the .AFH and stop at `AtMaterialOwner::GraphicsFactory` (slot 18, the owner's class is not recovered) unless a real owner is given. Next
is Text, which stops with a diagnostic, then Script, the same. So no real file loads to the end. Nothing recovered calls `ReadDefinition`: its caller, 0x00011B40, needs the player at +0x0C. Nothing recovered sets `AtAudioBankFile::s_context`
(0x002C6328, stored at 0x0001951A in 0x00019440), as with `AtIoFileRef::s_context`.

## What the green result does not show

* **What stands in, the same on both sides.** The graphics database loader (`AtDatabaseLoader::Load` 0x0001ADC0 and the texture count 0x0001C6F0, which have suites of their own), the owner, its factory and the loader object are the harness's. So the real
  .AGD files are not read here; the shapes' table is compared with the loader's answers as the harness gives them (1 database, 3 textures, and written variations). The scripts' and texts' loads (0x000134A0, 0x00013CB0) are logged, not run.
* **Real files reach only part of the format.** The 20 .XFF have 6260 frames and 17201 tags. All four kinds of tag occur; whether every place offset (name, transform, color) occurs in them is not counted. The FrameRefs forms `from:to` and `frame*times`, an
  empty name, each wrong mark and word, every heap and no-room path, pending and failed reads rest on written text and synthetic .XFF.
* **Not compared, uninitialised stack.** An .XFF whose second header read fails or comes up short leaves the counts' stack bytes as they were: the two sides differ. Not run.
* **Not run: a run backwards** in FrameRefs, `6:2`: the count is nearly 2^32 and it writes through the heap until it faults, on both sides, taking the harness's memory with it.
* **An .AFF with frames.** Its frame reader (0x000235C0) is not recovered; only `Frames[0]` is compared.
* A tag prepared twice calls its own Reset through the vftable, which is a diagnostic here: not reached by any file, not run.
* Directory pushes are checked to balance; a crash leaves one pushed, as in the game.

## The seam

`AtFlashHeapUser` is gone: the level's +0x154 and +0x248 are its shape and text tables, and 0x00058AF0 is `AtFlashResourceTable::SetHeap`, one store to +0x24, folded with other classes' setters at the same offset (two vftables in .rdata name it too).

## Quirks of the original, kept

* `AtFlashLevel::Reset` copies eight bytes from an empty string at 0x00270F0B, so the name holds the next seven: `\0%s.%s\0`.
* The sprites' Load stores the default heap into itself (0x00016F40 with its own value) before giving it to the sprites.
* An .XFF's frame list is not cleared, unlike the base's Allocate; every entry is written at once anyway.
* `FrameRefs` runs and repeats are not bounded: `1:6` in a list of 3 writes past it, and a run backwards writes until it faults. A run sets the first entry's name to null, again for each frame of the run.
* `from:to` gives the frames after the first; the first keeps the frame read. `frame*times` repeats the previous entry's frame, not the one read.
* A frame's tags are listed removes, places, actions, sounds, whatever order the header gives the counts in.
* A place's name, transform and color are found by offsets from the end of its record, so they sit in the data after the tags.
* 255 times the original's constant for 1/255 is not quite 1.
* The shapes' Clear reports a texture still held and frees all the same.
* `AtFlashResourceTable::RecycleGroup` with no groups crashes, and the sprites' and shapes' Clear recycle their groups without counting them down: the count stays.

## My mistakes

* The first mutant run: 62 of 462 survived. 31 were gaps in the harness, now closed: no-room paths were only ever hit at the first request (a push-counting hook now fails each request in turn), the file class was not tested on its own,
  tables were never loaded twice or destroyed loaded, groups never held a member when cleared, fields were never set to something for a Clear or destructor to reset, frame indices fit in 16 bits, and the long-name and no-brace .AFD paths were not written.
  31 were equivalent and are dropped with reasons; one more, the sprites' Clear zeroing m_heap after the base's Clear, was found on the rerun.
* A written FrameRefs run backwards, `6:2`, wrote through the harness's heap until it faulted, and the comparisons after it were garbage until I saw why. It is not run.
* The harness's own path strings were allocated while the recovered side was being logged, which showed as a difference in the first run.
* `AtFlashLevel::Reset` first copied an empty literal; the original's eight-byte copy takes the next seven bytes of the image, which the oracle found.
* Patches through shell heredocs lost backslashes twice, breaking the oracle's source; the brief warned of this.
* Early scratch files went to `C:\KND\analysis-local\scratch\afd\` (two disassembly listings); later ones are in the worktree's ignored `analysis-local/afd/`.
