## What a real build does with this

Still nothing reaches it from data: no creator walks the static list of create functions. Called directly, a real build now runs FaAcPlayer's slot 15 completely as far as its own code goes: it copies the level's name, reads LevelContinuation and the level's saved time, finds the head joint, sets the sight query up, makes and attaches a FaCmPlayerCombat when the record says Combat (reading the combat record twice, making the weapon sets and setting the health stat), and sets the target sprite up. Where it stops:

* Its first call, GmAcCharacter's slot 15, goes on to GmAcActor's slot 15 (0x0014AE90), which is not recovered and stops with a diagnostic ("Gm actor: GmAcActor slot 15 ..."). So a real build stops at once, before any of the above; the above runs only with that slot stood in, as the oracle does.
* Every record lookup reaches the registry's search by path (0x000679E0), a seam: so does FindComponent, which, unlike FindValue, does not test for a registry first.
* The combat module's update (slot 6, 0x000A4BB0) stops with a diagnostic; `test_plsetup --seam` checks it stops. Its slot 5 and Stop handle weapons, which only the update makes.
* On this branch nothing sets GmPlayerApp::s_instance, GmLevelManager::s_instance, GmHistoryLogs::s_instance or its scenes, GmSavedGame::s_instance (whose value is not read) or the heaps; a real build would crash reading them.

* **The stat setter**: FaCmCombat's Attach sets the owner's sHealth from its base, marks it changed, clamps it to its maximum and then its minimum (+0x10, +0x0C), and copies it back to the base: an inlined setter of GmAcStat, whose words +0x0C to +0x2C are now named.
* **0x002CB0A8 is more than the history logs**: its constructor 0x0006C2A0 sets the global to itself; game classes reach scenes through its +0x08, other objects through +0x0C and +0x10. Its +0x08's +0x90 is searched as a name map group, as AtNameTableOwner's is; the target sprite is set up from that object's +0x08, whose +0x10 is an AtMaterialOwner (the sprite calls its slot 21 and looks up materials at +0x78 and +0x90).
* App+0x65B8 is the saved game's values: an object with an AtDataRegistry at +0x04, read by section and name with a type (0x00144A50; 0x00144AE0, 0x00144B00 and 0x00144B20 for types 2, 1 and 3). 0x00305A48's readers (0x0009D920, 0x0009D950, 0x0009D980) do not read their own object.

## Quirks kept

* Slot 15 copies the level's name whether or not LevelContinuation is set, writes the saved time, a real, into the level manager's +0x60 (an integer in that header), and sets the sprite up through its vftable.
* The combat record is read twice by FaCmPlayerCombat's Attach; WeaponSets and EnemyPriorities found with the wrong type leave what was there; the attack ranges of a second read replace the first without freeing them. Reset leaves +0x60 (UseStartPositionForAttackRange).
* MakeWeaponSets runs once; each set is named only when its name is itself a value under the record, and copies the name as eight characters, terminated, to look it up. ReleaseWeapons tests each set's address for null. Stop lets go of the weapons without releasing them and frees the arrays; the list pointer is left for Reset. The destructors run Stop twice.
* The stat is clamped to its maximum first, then its minimum; a minimum above the maximum wins. A NaN stays, and slot 7 calls it dead.
* FindComponent and FindRecord measure the whole name only to test it for zero, and test neither registry nor record. The saved game's Find, given a section that is not found, looks for the name alone, from the root.
* The sight query set-up copies each measure as a word; without a position it does not test the scene node.

## Not compared, and why

* x87 against SSE: Set's squares are exact in a double and rounded once, as in the x87; the cosines are the x87's own fcos (AtCos) on a double argument, exact there, then rounded to a double and a float, where the x87 rounds its 64-bit result to a float once: a double rounding that no case showed. A signalling NaN health would be quieted by the original's x87 loads and kept here; no case uses one.
