# Skeletons, .AKC, and the base class of every texture

Worktree branch, for the integrator. State of everything here: Semantic-tested. Host compiler results are no claim about the original compiler.

## What .AKC holds

The executable never says. It has the three letters, as an extension, at 0x00273128, and no message that names the format. What the code and files show: an .AKC file is one `AtCoordSysDatabase`, read at 0x00026DB0 and called at 0x0001A692 for each name in a list the owner keeps (0x002C62AC). It holds a tree of named coordinate systems, and for some of them a matrix given in full.

```
RotTransCoordSys[n]            at least one of these two counts
ScaleCoordSys[n]
LocalDrawingTransform[n]       optional: how many entries give the word below
CoordSys
{
    RotTransCoordSys "rootR"   Position x y z, Orientation x y z w
    {
        Parent "name"          must have come earlier in the file
        LocalDrawingTransform  sixteen reals
    }
    ScaleCoordSys "name"       Scale x y z, or UniformScale s
    {
    }
}
```

Words are the original's, table 0x002B05F8. On the disc's 544 distinct files: 2,130 rotations, 65 scales, 1,220 drawing transforms; `UniformScale` is on no file. 474 files have no drawing transforms, most with one to three entries (for example `UI\TRANS\WIPE.AKC`: `bone0R`, `bone1R`); the 70 that do are mainly under `ART\CAST` with names such as `rootR`, `pelvisR`, `rtthighR`. "Skeleton" is my word for this, from those names. 0x00032940 multiplies `m_drawingLocal` by the world matrix into `m_drawingWorld`, and the values on real files look like the inverse of the pose at rest, which is what skinning wants: an inference from the numbers, not recovered code.

Each entry takes two matrices from the pool as it is made, and each drawing transform two more: hence `(rotTrans + scaled + extra) * 2` in `Allocate`.

## The texture item's class

0x000312D0 is slot 2 of vftable 0x00274A04, which has 11 slots; the float 127.5 follows it. It is the base class of the three concrete classes at 0x00289700, 0x0028B88C and 0x0028B8DC, whose readers call it first or jump to it, and whose destructors end by jumping to 0x00031290. It is what `AtTextureDatabase` called `AtTextureItem`; two more slots the database uses, 11 and 12, are in none of the base's table. So there are two names here: `AtTextureBase`, the class with that vftable, and `AtTextureItem`, the same object as the database sees it. Whether the original has a class between them is not known. 0x00031120 reads the word `ProgSource`, into a block of `{width, height, AtPixelFormat}` on the token file's heap. Width and height are inferred, from `ProgSource 128 128 32 1 16711680 65280 255 -16777216`, the only one on the disc, on `SHAPES\FETPSCRT.AGT`.

## Recovered

.AKC, `src/at/AtCoordSysFile.cpp`: 0x00026DB0 `AtCoordSysDatabase::Load`, 0x00026C10 `Read`, 0x000268C0 `NextMatrix`, 0x000324E0 `AtCoordSys::ReadWord`, 0x00032D40 `AtRotTransCoordSys::Read`, 0x00032C70 `AtScaleCoordSys::Read`, 0x00117080 `AtMatrixRead`, the table's reader of sixteen reals. Keyword table 0x002B05F8, compared with the bytes.

Texture base, `src/at/AtTextureItem.cpp`: 0x00031070 constructor, 0x00031290 complete destructor, 0x00031530 deleting destructor, 0x00030FF0 `Describe`, 0x000312D0 `Read`, 0x00031100 `ClearPending`, 0x000310C0 `Reset`, 0x00031260 `SetTransparentColor`, 0x00031050 `ClearTransparentColor`, 0x000311F0 `SetLightDirection`, 0x00031060 `ClearModifyUsage`, 0x00031040 `FreeProgSource`, 0x00031120 `ReadProgSource`, vftable 0x00274A04. Slots 8 and 9 are 0x000AB720, returning 0, folded.

20 functions and one vftable, against a budget of 60. The neighbours 0x00032690, 0x00032940, 0x00032A00 and the others that use the drawing matrices were left: nothing here needs them.

## Quirks kept

* The name of an entry is put in the map before its body is read, so `Parent` may name the entry itself. It then is its own child.
* `m_root` is the last entry with no parent when it ended. A file with several has only the last.
* `LocalDrawingTransform` given twice in an entry takes two more matrices, and the first two are left.
* The word `LocalDrawingTransform` with no count for it at the head: the report, then a read through null.
* An entry past the count is reported and then read over what follows the array.
* `AtTextureBase::Read` clears usage, flags, levels and stage, but not the colour, light direction or `m_progSource`; a second `ProgSource` loses the first block.
* `PlatformSource` is `DDSSource` with a flag. A source is a field set whole, so the last word wins: the disc has six more source words than items, which reads as six items giving two.
* `MipMap` compares its byte: 256 is 1, not 256. `Describe` compares the whole value and then cuts it: 256 is 0.
* `Reset`, and the destructors, write only the first byte of the name.
* `m_transparent[3]` stays 0xFF through the file's word, which gives three values; only `SetTransparentColor` sets it.

## Oracles

`python -I tools/oracle_run.py --suite akc`, for .AKC. All 544 distinct files, each loaded, loaded over itself, cleared, loaded, destroyed; about 140 written texts for each word and error path, under two heap fills, with the report returning (up to 40 of them, then a deliberate crash, on both sides) and with the load ending at the first report, as the game's does. The matrix reader and `NextMatrix` by themselves. A pool that answers one matrix more than it holds reaches the second report, since a file's are reserved in twos.

Result on 2026-11-07: `NO DIFFERENCE OBSERVED: 544 files, 2130 rotations, 65 scales, 1220 drawing transforms, 544 with a root; 1409276 comparisons, 0 differences`; 7/7 entries; positive control passes; `--mutate` fails; 116/116 source mutants detected. `verify.py --only` shows MATCH, MISMATCH or SIZE for each function and MATCH for the vftable.

`python -I tools/oracle_run.py --suite agt`, the texture database's suite, now with the real reader on both sides. On the original's side an item is built by its own constructor and given a table of its own slots, but for slot 2, its own reader wrapped to log, and the concrete class's slot 12. All 579 files, under five states of what the owner knows. Every field of every item is compared, with `ProgSource`'s block. Added: the reader by itself, for each word alone, each word after each source and two others, new and with everything set, under two heap fills; the frame of a body; `ProgSource` with no heap and no memory; `Describe` over a grid; each small slot; 3,016 light directions, including zero, NaN, infinity and very large and small ones; constructors and destructors byte for byte.

Result on 2026-11-07: `NO DIFFERENCE OBSERVED: 579 files, 2358 textures, 2424 surfaces, 112 on demand; 1100673 comparisons, 0 differences`; 26/26 entries; positive control passes; `--mutate` fails; 306/306 source mutants detected, the 187 of before and those of the item. `--suite all --no-mutants`: 22 suites, no differences, every entry reached. The asn suite's mutants were not rerun: its source changed only by renames, and its mutant texts were checked to occur.

Real items: source bmp 4, tga 52, dds 2,300 of which platform 1,436, tpl 1, prog 1; 66 with more than one level; 112 on demand. No real file has tm2 or pnt, or any item with `LightDirection`, `TransparentColor` and the rest: those are compared only on written text.

Doubles, on both sides, so no evidence about them: in akc, the matrix device, the pool, and `SetTranslation`, `SetRotation`, `SetScale` and `SetUniformScale`, which log every value and keep them in the matrix. The reader of matrices is the original's own. In agt, the concrete classes and slots 2 to 13 of the database, as before. The test item adds logging around the reader, and for the word `Tm2Source`, on no real file, names itself after reading, to show the order in the database's `Read`.

Not comparable: a name that is not a string leaves stack bytes as the name, after the report. Those seven texts (an entry with no name or a number for one, `Parent` likewise) run in akc only to the report. In the game the report does not return, so nothing is lost there, but what the code would do past it is not compared.

## Shared edits

In `include/at/AtCoordSys.h`: `AtMatrixTable` gains `SetUniformScale` and `Read`, at the end so that no harness breaks, so its order is no longer that of the addresses. `AtMatrixPool::Slot3` is now `Count`, returning the count: anything deriving from the pool must change, as `test_asn` and `oracle_asn` have. `m_unknown10` and `m_unknown1C` of `AtCoordSys` are now `m_drawingLocal` and `m_drawingWorld`, and `m_unknown2C` of the database `m_root`, with `AtCoordSys.cpp`, `oracle_asn.cpp` and `suites/asn.py` following. `AtTextureItem` moved to its own header, included by `AtTextureDatabase.h`, and its slots to `AtTextureBase`. `test_agt`, `oracle_agt` and `suites/agt.py` changed for the real reader.

## What a real build does

`g_atMatrix` still stops with a diagnostic for all but `Read`, until the graphics layer's 0x000EC2B0 is recovered, so a real `.AKC` load stops at the first entry's `SetMatrices`. The concrete texture classes are not recovered either, so no real `.AGT` load runs beyond the harness. Both readers are compared on real text, but only through those stand-ins.

## Mistakes of mine

* Seven akc mutants survived the first run, all of the dirty bits, and one of agt, the reader calling `SetLightDirection` other than by its slot. In a file every entry is new with all those bits set, and every concrete texture has the base's slot 7, so real text cannot show either. Gaps in the harness, closed: `run_entries` calls an entry's reader with its bits changed first, and the test item has a slot 7 of its own that logs. So for real files those lines are not otherwise exercised.
* Four of my first mutants did not compile, and stopped the run: a declaration jumped by a `default`, and enum values that made two cases equal.

* The x87 stack: a crash storing a real through a null matrix leaves that real on the stack, and the guard does not restore the x87. After eight of them, the reader got NaNs on one side and values on the other, and showed as 14 differences in a text that had nothing wrong with it. The akc harness resets the x87 after each load. That was a fault of the harness, not of the code, and I took it for the latter at first.
* First harness ran the name-not-a-string texts past the report, and compared stack bytes. See above.
