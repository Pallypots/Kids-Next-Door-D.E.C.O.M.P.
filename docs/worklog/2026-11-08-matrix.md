# The matrix table, g_atMatrix (2026-11-08)

Worktree branch, for the integrator. This file holds what belongs in docs/verification.md and docs/portability.md. State of everything here: Semantic-tested. A host MATCH from `tools/verify.py` says nothing about the original compiler.

## What a real build now does on real files

**.AKC.** `g_atMatrix` no longer stops with a diagnostic: every member is a recovered function, the one 0x000EC2B0 puts in that slot of the original's table. The `.AKC` reader and the coordinate systems (`SetMatrices`, `SetRotation`, `SetTranslation`, `SetScale`, `SetUniformScale`, `Read`, `UpdateWorld`, `UpdateInverse`, `Transform`) now compute real matrices in the host build. What still stops a real `.AKC` load in a real build is the **matrix device**: `AtCoordSysDatabase::Load` is given an `AtMatrixDevice`, by the owner's slot 0x44 at 0x0001A68C, and that device and its pool (`NewPool`, `Reserve`, `Count`, `At`) belong to the graphics layer, which is not recovered. In tests a stand-in device hands out plain arrays of 64-byte matrices. **On the disc's 544 distinct `.AKC` files, the matrices come out the same as the original's own functions give, bit for bit**: `oracle_matrix` reads each file with the host's reader twice, once with `g_atMatrix` holding the original's functions from its own filled table and once the recovered ones, updates every world matrix, transforms a point through each and updates every inverse: 2,195 coordinate systems, 6,830 matrices, 1,220 drawing transforms, no difference. Only the matrix functions differ between the two runs; the reader and coordinate systems are the host's on both, compared with the original in the akc and asn suites.

**.ASN.** The scene reader calls the same table, so its matrices are now real too. But `test_actor <file>`, the scan that loads the 652 real `.ASN` texts, still installs its own matrix stand-ins in `set_tables()`, and its stand-in device hands out **12-byte** matrices (`struct Mat { float position[3]; }`). Pointing that scan at the real table means changing that device to give 64 bytes per matrix, aligned to 16 if the original's own functions are ever called through it, and removing the ten `g_atMatrix` assignments. That file is the actor subsystem's; I did not change it. Until then the `.ASN` scan says nothing about matrices. Beyond matrices, a real `.ASN` load still needs everything the particle worklog lists: the device, the owner's tables, the emitters and drawers.

**Textures.** The concrete texture classes are **not in reach** of this budget. By the closure script, the 2D texture's vftable 0x00289700 reaches 166 unrecovered functions (29,210 bytes) and 0x0028B8DC 170 (31,735 bytes), mostly D3D resource creation and image decoding, in the 0x0005F000-0x00065FFF and 0x000FC000-0x00122000 ranges, plus the C library. The third, 0x0028B88C, reaches only 15 (447 bytes, much of it the C library's `operator delete`), but its slots 11 and 12 do nothing (0x000FCD40 and 0x000CBF30 are 3-byte returns), so on its own it would not load a texture: which items get that class, and why, belongs with the concrete texture database 0x0028A6E0, also not recovered. So no real `.AGT` load runs beyond the harness, as before.

## The table

0x002C60C8, 104 slots of 4 bytes, every one written by 0x000EC2B0 (`mov [eax + offset], function`), which 0x000EC670 calls for this table and again for a second table at 0x002C7C48. 0x000EC670 then writes seven more pointers at 0x002C7DE8, just past the second table. A scan of every 4-byte value in `.text` that falls in the table's range finds no other writer: 524 references, all calls or loads (`analysis-local/scratch/matrix/writers.py`). 0x000EC2B0 is not recovered as a function, since 65 of its 104 targets are not; `g_atMatrix` is initialised with the targets of the 39 slots it names instead, and the oracle runs the original's 0x000EC2B0 to check each slot holds the function the member is compared against.

Of the 104 slots, 44 are read by some code in the game (`uses.py`), counting the twin table. The 15 the recovered code calls, and 24 more of those 44, are recovered. Not recovered: 60 slots no code reads, and 5 that some code does: the rotations about one axis 0x00117EE0, 0x00117F40, 0x00117FA0, 0x00118100, which build a rotation on the stack with `fsin` and `fcos` and multiply through 0x001155F0 or 0x00115850, and the matrix to quaternion 0x001163D0.

Two kinds of code sit in the table. 0x00105440-0x0010588F is hand-written or intrinsic **SSE** (`movaps`, `mulps`, `shufps`, `prefetcht1`): Copy, SetProduct, ScaleAxes and Transpose of those recovered. The rest is compiled **x87**. The SSE slots are written last by 0x000EC2B0, the x87 ones first; slot Copy is the SSE copy, while Multiply calls the x87 word copy 0x00114FB0, which no slot holds. So `Multiply(m, by)` and `SetProduct(m, by, m)` do not give the same bits: one rounds each product to float and adds in single precision, the other keeps the sum in a register.

## Quirks kept

* **Aliasing is part of the behaviour.** `SetInverse(m, m)` writes the position first and then reads it back as it transposes. `Multiply(m, m)` reads `by` as it writes `m`, since only `m` is copied first. `TransformPoint(m, v, v)` stores after every step and reads `from` again each time. `SetProduct` reads all of `b`, then the first two rows of `a`, writes two rows and only then reads the last two rows of `a`: so `to` two rows past `a` reads what it has just written. Each is compared.
* **Signalling NaNs.** Most elements are moved as words and keep a signalling NaN as it is. Where the original moves an element through an x87 register instead, it is quieted: element 0 of `SetUniformScale` (5 and 10 are words), `SetElement`, and elements 4 and 8 of `Invert` (1 and 2 of the original, while 1, 2, 6 and 9 move as words). The source keeps this with `ThroughRegister`, a round trip through a `volatile double`.
* **SetRotation does not need a unit quaternion**: it divides by the squared length. A zero quaternion gives infinities and NaNs. It writes only the 3x3.
* The three look-at functions differ only in which axis the direction and the up become. Each normalises the direction, takes the part along it out of the up and normalises that; an up along the direction gives (1, 0, 0) from `Normalize`'s shortest length.
* `Invert` is `SetInverse` in place but not the same code: it keeps the old position in registers, and leaves the fourth column as it was where `SetInverse` writes 0, 0, 0, 1.
* `TransformPointZ` returns the z of a transformed point, summed in another order than `TransformPoint`'s, in st(0) without rounding. The source returns a `double` so that a caller rounds where the original's would store. `GetElement` returns a float in st(0): no extra bits there.
* `ScaleAxes` reads 16 bytes from a three-float vector (`movups`): one float past it, not used. The original's `Copy`, `SetProduct` and `Transpose` need 16-byte aligned matrices (`movaps`); the source does not.
* `MakeRotation` and `MakeAxisAngle` rely on `ecx` keeping the matrix across the call to 0x001150F0, which does not touch it: a compiler that knew its callee. Nothing to keep in source.

## Oracle

`python -I tools/oracle_run.py --suite matrix`. The original's 0x000EC2B0 fills a table of the harness's; each of the 39 named slots must hold the function read for it, and then each is called through that slot against the member of `g_atMatrix`, plus the two helpers directly. 200,000 rounds of ordinary and edge values, a quarter of the matrices a real rotation and translation, a quarter built from three values and their negatives so that products cancel exactly and the order of a sum shows; 50,000 rounds with infinities and NaNs; 50,000 with signalling NaNs. Every output starts with the same random contents on both sides, so what a function must leave alone is compared. Elements only moved are compared bit for bit, NaNs included; results of arithmetic count two NaNs as alike, counted apart, since which NaN comes out of two is not the same between x87 and SSE. Aliasing and overlap as above. A look-at with an up across the direction, so that two terms of the dot product cancel exactly.

Result on 2026-11-08: `NO DIFFERENCE OBSERVED: 191816449 comparisons, 0 differences`, with the `.AKC` pass `544 files, 2195 coordinate systems, 6830 matrices, 1220 drawing transforms`; entries reached 40 / 40; positive control passes; `--mutate` fails; **106/106 mutants detected**. One mutant is left out as equivalent on this harness, with the reason in the suite: holding `ThroughRegister`'s value as a `volatile float` still quiets a signalling NaN on x86, since a returned float goes through st(0); the x64 host test checks the quieting where that would not hold. `verify.py --only` over the 40: 11 MISMATCH, 29 SIZE, none MISSING or UNRESOLVED.

Precision: x87 at 53 bits, the game's main thread's (docs/portability.md). MXCSR: no `ldmxcsr` anywhere in the XBE (`mxcsr.py`, every section), so the SSE functions run under whatever the kernel sets; the harness uses the host's default 0x1F80, round to nearest, no flush to zero. That denormals are not flushed on the Xbox is **not established**.

What a green result does not show: the angles of `SetAxisAngle` and `MakeAxisAngle` go through `AtQuaternion::SetAxisAngle`, whose sine and cosine the host gives (src/at/AtMathHost.cpp uses `fsin` and `fcos` on x86); they are compared on x86 and left out of the x64 hash. Callers of `TransformPointZ` and `GetElement` are not recovered, so what a caller does with st(0) is not modelled beyond returning a double. NaN sign and payload from arithmetic are not claimed.

## Portability

* x87 to SSE: `double` where the original keeps a value in a register, `float` where it stores, gives its bits at precision 53 with SSE2 arithmetic, on x86 and x64 alike, provided the compiler does **not contract** a multiplication and an addition into a fused one. `src/at/AtMatrix.cpp` turns contraction off for MSVC (`#pragma fp_contract(off)`) and clang (`#pragma STDC FP_CONTRACT OFF`). **GCC ignores the standard pragma and contracts by default** for GNU C++: an ARM64 or x86-64 GCC build needs `-ffp-contract=off` for these files at least, or its results will differ in the last bit. That is a build flag for the integrator to decide; it is not set anywhere yet.
* Exponent range: x87 at precision 53 still has a 15-bit exponent, so a sum that overflows or underflows a double in the middle would differ. Products of two floats and sums of four cannot reach that, so for these functions it does not arise.
* An x86 build with `/arch:IA32` (x87 code) would differ: it would quiet signalling NaNs on every float move and round differently. The oracle and verify builds use the default SSE2.
* Signalling NaNs: `ThroughRegister` relies on float-to-double conversion quieting them, which SSE `cvtss2sd` and ARM64 `fcvt` both do, keeping the payload, as x87 `fld` does.

## Mistakes of mine

* First mutant run, 57/61: four survivors, all gaps in the harness or my mutants. The overlap case put `to` one row into `a`, where nothing read is yet written; it now overlaps by two rows. A reordering of `SetInverse`'s sum and of the look-at dot product could not show on random values, which almost never cancel; I added matrices built from three values and their negatives, and an up across the direction. The look-at mutant itself only swapped two terms, which is the same sum by commutativity; it now moves the third term first. The fourth, `volatile float`, is equivalent on x86, as above.
* Second run, 105/106: the order of the four squares in `SetRotation`'s denominator survived 240,000,000 random quaternions searched offline, since an ulp of the denominator reaches a float only at a rounding midpoint. Quaternions with two equal components and two small make `1 - (zz + xx)` cancel, and about one in six then shows the order (`search_rotation.py`); the generator now makes those.
