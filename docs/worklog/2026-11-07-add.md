# 2026-11-07: the data library, .ADD, and the database manager, .ADB (subsystem `at/add`)

Reference build knd-xbox-usa-5454008a-v1. State of everything here: Semantic-tested. No original-compiler match (blocked, docs/toolchain.md).

## What the format is, from the code and the disc

* `.ADD` is text through the shared tokenizer, keyword table 0x002B47F0 with two words: `DataRegistry` (0x39) and `DatabaseManager` (0x3A). Each is followed by `[ n ] { "name" ... }`. Anything else is reported (code 0x1E) and reading goes on. A second list of the same kind is reported (code 0x27) and replaces the first, leaking it.
* Each `DataRegistry` name is loaded as an `.ADR` through the registry at 0x000674E0 / 0x00068880; each `DatabaseManager` name as an `.ADB` through 0x000B2330. All names are read first, the file is closed, and the entries are loaded with the `.ADD`'s directory pushed on the path.
* Start-up, 0x0008DEA0, loads `Design\Registry\Generic.ADR` into App+0x6950, then `Library.ADD` into the library at App+0x6B40, as `Load(owner, "Library", 0, parent)` where owner is offset 0x394 of the object at 0x003B357C and parent is offset 0x2C of that object. 0x0008ED60 calls the library's Clear.
* **The disc has exactly one `.ADD`, `AppInit.JAM`'s `LIBRARY.ADD`, holding only a `DataRegistry` list of 11 names (`Design\Registry\Actor` ... `Weapon`), and no `.ADB` in any archive** (a scan of every archive's directory: 1 ADD, 0 ADB, 311 ADR). So on this disc the whole `.ADB` half is never reached; it is recovered because it is what the reader alone needs, and it is tested on written text only.
* `.ADB`, keyword table 0x002B5310 (34 words, names in the binary): an optional `NameSpace "x"`, then `DataComponentDescs[n] { DataComponentDesc { Name Type NumElements Floor Ceiling FormatString } ... }`, `RecordLayoutDatabases[n] { RecordLayoutDatabase { Name "x" Desc "..." DataComponents[n] { "field" ... } } ... }`, `DataRecordDatabases[n] { DataRecordDatabase { Name Desc RecordLayout "layout" DataRecords[n] { values ... } } ... }`. Values are read by the value classes of the `.ADR` work, by type: Boolean 1, Int 2, Real 3, ShortName 4, String 5, BooleanArray 6, ByteArray 7, IntArray 8, RealArray 9, ShortNameArray 10, StringArray 11; `Relational` gives 12, which no table holds. `Byte`, `Flags`, `Database`, `RelatedField`, `ReferencedField` are in the table but rejected where they could appear.

## Seams (`src/at/AtDataLibraryHost.cpp`), each stopping with a diagnostic

The registry, the descriptor's other members and the eleven value classes are held by the `.ADR` work on another branch (`include/at/AtDataRegistry.h` there). Each seam in `include/at/AtDataLibrary.h` names the one line it becomes when that arrives: `new AtDataRegistry`, `registry->m_loaded`, `registry->Clear()`, `delete registry`, `registry->Load(...)`, `new AtDataDescriptor[n]`, `delete[]`, `descriptor->Clear()`, `new AtDataBoolean[n]` and the like by type, `delete[]`, `sizeof`. Three members of `AtDataString` that only this reader calls, 0x0006A1D0, 0x0006A4D0, 0x00069FD0, are not recovered by either branch; they reach the text classes.

`AtDataDescriptorFields` and `AtDataValue` stand for `AtDataDescriptor` and `AtDataComponent` of that branch, with the same layout and slot order; they are to be deleted when it is merged, and `Read` moved into `AtDataDescriptor`. `AtDataOwner` is the same object as that branch's `AtDataRegistryOwner`: its groups at +0x08 and +0x20 run straight into theirs at +0x44 and +0x58.

**What a real build does on real files now:** it reads `LIBRARY.ADD` to the end, makes its list of 11 registries, and stops at the first, with "the .ADR registry is not in this build". With the `.ADR` branch merged and the seams replaced, the library would hand each of the 11 names to the recovered registry loader; that combination has not been run.

## Quirks of the original kept

* The library reads each name into a 0xFF-byte buffer though a string may take 0x100 bytes with its terminator: the longest string overruns it by one.
* `Clear` of the library does not free the name lists; it forgets them.
* The manager's constructor empties the list of managers before joining it, so the list only ever holds the newest; Clear empties it too.
* A record table's constructor leaves its layout and records pointers, so destroying a table never read crashes on what the heap left; Clear leaves both, so a second Clear, or destroying after one, crashes too (both checked against the original).
* The descriptor reader skips anything up to the first left curly; a file that ends first never returns.
* A layout's map holds the address of each slot of its field list, not the descriptor; a field no descriptor names is null, and a table on it crashes.
* A table's layout is looked up by name in the manager's own map, which also holds tables: a table name there is taken as a layout.
* `FieldNamed` with no match asks for the column past the last.
* A map of no size divides by zero in the original's lookup: `FindEverywhere` on a manager never loaded crashes.
