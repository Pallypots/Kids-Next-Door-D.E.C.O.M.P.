# The .AGD lists

Worktree branch, for the integrator. State of everything here: Semantic-tested. Host compiler results are no claim about the original compiler.

## What .AGD is

The executable never says. The three letters are an extension at 0x002723CC, and the words are at 0x002B0190. From the code and all 423 distinct files: an .AGD is a list of other files to load, by kind, with nothing else in it.

```
TextureDatabase[1]
{
    "Name"
}
MaterialDatabase[2]
{
    "A\B"
    "C"
}
```

Eighteen words: `TextureDatabase`, `ShaderDatabase`, `MaterialDatabase`, `MeshDatabase`, `LightDatabase`, `CoordSysDatabase`, `CoordSysMirrorDatabase`, `WeightsDatabase`, `AnimationDatabase`, `MatAssignmentDatabase`, `MatAnimationDatabase`, `MorphAnimationDatabase`, `LightAnimationDatabase`, `FontDatabase`, `ImageDatabase`, `VertexProcessDatabase`, `PixelProcessDatabase`, `DatabaseLoader`.

Uses on the disc's distinct files (lists, then names):

| Word | Lists | Names |
| --- | --- | --- |
| MaterialDatabase | 420 | 688 |
| TextureDatabase | 414 | 652 |
| MeshDatabase | 352 | 461 |
| CoordSysDatabase | 289 | 699 |
| AnimationDatabase | 289 | 699 |
| ShaderDatabase | 228 | 298 |
| MatAssignmentDatabase | 62 | 67 |
| LightDatabase | 16 | 16 |
| MatAnimationDatabase | 7 | 7 |
| FontDatabase | 1 | 1 |
| ImageDatabase | 1 | 1 |

The other seven words are on no file. Three comments occur.

Order in the file does not matter to loading: 0x0001A4B0 goes vertex processes, pixel processes, textures, shaders, materials, meshes, lights, coordinate systems, mirrors, weights, animations, material lists, fonts, images, material animations, morph animations, light animations; frees the names; then nested loaders. Names are relative to the .AGD's own directory, which is pushed while they load.

## Not recovered: the seam

Four kinds stop with a diagnostic through `AtFatal`, naming the address and the extension: `CoordSysMirrorDatabase` (0x00019D30, .AKM), `WeightsDatabase` (0x00019E70, .AKW), `MorphAnimationDatabase` (0x0001A1F0, .AGO), `LightAnimationDatabase` (0x0001A310, .AGH). The seam stands for the members `m_mirrors`, `m_weights`, `m_morphAnimations`, `m_lightAnimations` and those four functions; replacing it means deleting the four function bodies and adding the arrays, their loops in `LoadDatabases` and their lines in `Unload`.

On the address list and not done, for budget: 0x00027340, 0x000274F0, 0x00027880, 0x000279F0, 0x000284E0, 0x00028C30, 0x00028DA0, 0x00029AF0, 0x00033340, 0x000333E0, 0x00034550, 0x000350E0, 0x00035670, and 0x00019D30, 0x00019E70, 0x0001A1F0, 0x0001A310. With the classes they need, about 27 more functions. No .AGD on the disc lists any of these four kinds, so nothing real reaches them. I read all of them; the reading is not written down beyond these notes, and the next agent should expect mirror 0x50 bytes per entry in a database of 0x38, weights 0x10 in 0x1C, morph 0x20 in 0x5C, and light animation 0x40 in 0x94.

## What a real build does on real files

Not much yet, and not because of this reader. The concrete loader, at vftable 0x0028A7D0, made at 0x00112D60 in the graphics layer, is not recovered. So a build has no class it can make: `AtDatabaseLoader` is abstract, and nothing in the game's own path reaches `Load` until that class exists. Likewise the concrete mesh database, vertex arrays, meshes, keys, and textures.

With a concrete class supplied, on any real .AGD: the file is read, the lists are made and named, and each file named opens through the file system. Meshes and animations at mode 2 ask the database whether it has a binary form, and go to its slot 7 and slot 3 if so. The mesh base says no (slot 6 returns 0, slot 7 does nothing), so a concrete database must override them; I take that to be where `.XGG` and `.XKA` are read, an inference, since those readers are not found.

**There is no .AGG, .AKA, .AGV, .AGP, .AKM, .AKW, .AGO or .AGH file on the disc.** So these text readers are dead code on this release, kept in the executable. They are recovered because they are what `LoadDatabases` calls, and their words tell what the disc's binary forms hold; on a real run with binary forms present they do not run.

## Oracle

`tests/oracle/oracle_agd.cpp`. The doubles matter more than usual here, so first what it does not show: every file an .AGD names opens as empty text on both sides, and the concrete loader, databases, meshes, vertex arrays and keys are the harness's. So real .AGD files show the list, the sizes, the order and each path opened agree, and that each database's own Load runs and does the same on empty text. They do not show any real mesh, texture or animation loading. The .AGG, .AKA, .AGV and .AGP readers see only text written in the harness.

One class serves both sides for a slot called through a table, since x86 thiscall is what the original expects: objects on the original's side are made by the original's constructor over a fill, then given the harness's table. A slot the original reaches that has an original body (Clear, Unload, the material database's Load and Read) dispatches on the side, so that each side runs its own.

Not compared: a name where a string is required, which leaves the buffer as uninitialised stack on both sides. The seam's four words, other than that the recovered side stops. `delete[]`'s vector deleting destructors, compiler-made.

The names in the statics are freed before `Load` returns, so the oracle compares them through the paths opened and, directly, by calling 0x0001A4B0 with freeNames 0 on lists given by hand.

## Quirks of the original

* The name lists are statics shared by all instances, except the nested loaders' own, which is a member. A constructor or `Unload` of any loader empties all of them. If a concrete `MakeLoaders` constructs its children, as the harness's does, any list before `DatabaseLoader` in the file is lost and loading it crashes (0x0001A55A). Oracle: crash on both sides. No file uses the word.
* A second `Animation[n]` list in .AKA: reported, then `Init` finds a table and calls `Clear` through the table, which frees the keys and the new list; the end of `Read` then calls through a null `m_keys`. Crash on both sides.
* `AtVertexProcessDatabase::Clear` leaves the map as it is, unlike the pixel processes'.
* Index flags: `Index8Bit` then `Index32Bit` gives 8 bit, by the test order. `Index16Bit` clears both.
* `AtMathTriangle::m_axis` is 0 when Z is largest, with X and Y compared first so that a tie goes away from Z.
* 0x000333E0 builds a message in a local buffer and never uses it (not recovered, noted for whoever does).
* `AtFreeNameList` and `AtJoinPrefix` take a `this` they do not use. 0x000BB1C2 calls the first from elsewhere, so a whole-program build must keep its convention in mind.
* `prefix` reaches images alone. Nested loaders always get none.

## Shared edit

`include/at/AtMaterial.h`, `AtMaterialOwner`, additive with one retype of layout filler:

* It is now polymorphic, as the original is: slot 17 is called by 0x0001A68C. Slots 0 to 16 are empty and unnamed, slot 17 `MatrixDevice` stops with a diagnostic unless overridden. `m_unknown00[0x30]` became `m_unknown04[0x2C]`; nothing used it.
* `m_unknown31[0x0B]` became `[0x07]` and `m_animationDevice` at +0x38.
* `m_unknownF0`, `m_unknown21C` and `m_unknown2D0` are carved into the tables they hold: `m_meshes`, `m_meshSpaces`, `m_morphAnimations`, `m_morphAnimationSpaces`, `m_lightAnimations`, `m_lightAnimationSpaces`, `m_coordSystems`, `m_mirrors`, `m_weights`, `m_animations`.
* The header declares `AtFatal`, which every target links or doubles.

A possible double name: `AtMatrixDevice` here is what `AtCoordSysDatabase::Load` already took. `AtNameTableOwner` has its own `m_unknown08` of that type: whether the two owners are related is not established.

## My mistakes

* Named the file-format enumerators in `AtMeshDatabase.cpp` the same as `AtIndexArray`'s flags, so inside the member function the case labels were the flags. The oracle caught it at once.
* Used 0x00029B90 for the image database's constructor; it is 0x00029BA0. A crash found it.
* The harness kept a `std::string` alive across a logged call, whose destructor logged a delete on one side only.
* The first full mutant run left 21 survivors out of 361. Fourteen were gaps in the harness, now closed: directories at each open, the stack's bytes, nested loaders with a mesh and an image, stale index flags, a key set read twice, an animation read over, each static reset, the destructor with and without an owner, the joined name with no heap. Seven were equivalent or badly written, and were dropped or rewritten with the reason at the head of the suite.
* Took the mesh database's slots 3, 6 and 7 for pure until verify showed the vftable had bodies there.
