## The format

Text, through the ordinary tokenizer. 103 distinct files in the jams, under `DESIGN\REGISTRY\` and `DESIGN\LOCATION\...`. The words come from the table at 0x002B2690.

```
[NameSpace "Name"]
DataComponentTypes[n] { DataComponent { Type T NumComponents c } ... }
DataRegistry[n] { DataLink { Name "N" Type T Parent "A\B\" NumElements e Floor f Ceiling c FormatString "F" Data ... WillAcceptParentData } ... }
```

Twelve types: Empty, Boolean, Int, Real, ShortName, String, and arrays of Boolean, Byte, Int, Real, ShortName, String. The real files use all but ByteArray; none uses FormatString or a Unicode string. The first list sizes a pool per type; the second fills a tree of named values, which can hang in a parent registry's tree. It is the game's tunable design data: `Gravity`, `DamageParticles`, actor prototypes inheriting by path.

## What a real build does on real files

`AtDataRegistry::Load` reads every real file to a complete tree, alone and chained under the file before it in its archive, and files it with the owner. Then nothing in the game can read it, because:

* The readers of values, the value classes' slots 5 to 9 (`ElementAt`, `SetElement`, `Equals`, `RemoveAt`, `Write`), and the registry's lookups by path (0x000679E0, 0x000678A0, 0x00067950, 0x00067CB0, 0x00067CF0, 0x00067D20, 0x00068860) and its other loading form (0x000687D0, 0x00067200, 0x00068720) are not recovered. Slots 5 to 9 and the base's slot 4 stop with a diagnostic through `AtFatal`. The lookups do not exist in source yet.
* The owner, the class with vftable 0x00277420, is only its two members at +0x44 and +0x58. Its constructor is not recovered, and no game code constructs it here.
* No caller of 0x00068880 is recovered. Nothing in a build calls the loader but the tests.

## Quirks of the original, kept

* `SetFormat` allocates the text's length with no room for the terminator, and copies the terminator: one byte over. No real file has a FormatString.
* A reload loses things. `Load` stores a new file name, then `Read` clears: the clear frees that new name and resets, so afterwards the file name is null, the old name has leaked, and the owner and parent members are null. The registry is filed with the owner again, but with `m_owner` null a later clear does not take it out, so the owner holds a stale pointer once it is destroyed. A reload under a parent attaches the root first and then clears; the root can stay in the parent's list.
* A link's type and value carry on from the link before. Data with no Type yet indexes pool 13, off the end of the array into the members after it.
* A link with no `Data` crashes on the null link. So does `WillAcceptParentData` before `Data`.
* Bounds are read by the type given so far: `Floor` before `Type Real` reads an int and is lost.
* `Clamp` goes by the current type, not the value's class. Changing `Type` after `Data` clamps through the wrong class, and can crash.
* `DataLink` skips every token up to its `{`, and a link reads words to its `}`. At the end of the file that is forever if the report comes back. In the game `AtFatal` stops first.
* A String followed by a second string: if the second is "Unicode", ignoring case, the value is wide. The tokenizer holds one string at a time, so the value's text is then the second string, "Unicode" itself.
* Wide `AtDataString` clears half its block. Each element of a StringArray is wide text.
* A ShortNameArray goes through a name on the stack, so bytes past a short name's terminator are stack garbage. A ShortName goes straight in, and keeps the heap's fill.
* `AtDataInt`, `AtDataReal` and `AtDataShortName` leave their value uninitialised; `AtDataBoolean` and the arrays clear theirs.
* `AtDataStringArray::Reset` with nothing held leaves the base's fields. `SetText` does not free what was there.
* `Parent` falls back to the whole text as a name in this registry's own pools, ignoring case, and then to the root. A missing parent is never reported.
* `AtText::SetNarrow` writes its terminator at the capacity if the text fills it: one past.
* The ByteArray clamp tests each byte against 0xFF, which does nothing but read them.
* `FindByName`'s exact flag does not carry on to a chained block.
* `ElementAt` measures the index against each block's own count; it does not reduce it along the chain. So the callers' indices only reach a chained block when it is larger.

## Decisions

* The pools' arrays use `AtNewArray` and `AtDeleteArray` from `src/at/AtSceneArray.h`, with a switch on the pool's type for the values. The original does one `delete[]` on a base pointer through the vftable. I tried real `delete[]` and it corrupted the heap: every translation unit emits its own vftable with the scalar deleting destructor, and the linker may keep that one, so `delete[]` through the vftable is not safe with this compiler. The result matches the original when a pool's type agrees with its values' class, which holds everywhere pools are made.
* The deleting forms at 0x000661A0-0x00066680 are vector deleting in the original and recorded by the host's `??_G` symbol, as 0x0002E510 is.
* `AtDataRegistry.cpp` and `AtDataComponent.cpp` each have their own small text helpers, so that neither file needs a C library header.

## What the oracle does not show

* No game code runs on top of these. The test is of the loader and its structures, not of the game's use of the values.
* The owner is two members built by their own constructors, not the real class.
* The third allocation of `AtDataComponentPool::Allocate`, the links, cannot be refused alone: the harness's flag refuses all or none, and refusing all crashes at the descriptors first. Its raise has no mutant, and so is not shown.
* `Load`'s raise when the file name gets no memory is not shown either: the stream's and tokenizer's blocks come first in the same call, and refusing those means no tokenizer. Its mutant is dropped, with the reason in the suite.
* The refusing reader can only switch the flag at a tokenizer word, so failures inside one word's work are all-or-none.
* Five loads filled the fixed call log. Past that point their calls are not compared, though the final state still is.
* Unterminated links and links fewer than declared are not run: they do not end in the harness, whose report returns. See the quirk above.
* Data before any Type is only compared up to its crash.
* Names past a terminator in ShortNameArray are not compared: stack garbage on both sides.
* Reals are compared by bits, on an SSE host build; the original is x87. The clamps are compared with NaNs and infinities.
* Value class vftables are not recorded as vftables, since slots 5 to 9 are not recovered. Their addresses are in `[symbols]`.
