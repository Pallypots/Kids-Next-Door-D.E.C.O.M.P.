Worktree branch, for the integrator. State of everything here: Semantic-tested. Host compiler results are no claim about the original compiler.

## The format

A file is `Surface2D[n] Texture[n] Texture2D[n] { Texture2D "name" { ... } ... }`, optionally with `Surface3D[n]`, `Texture3D[n]`, `CubeMapTexture[n]`, and `NameSpace "x"` as the first word. On the disc's 579 distinct files: 2,358 textures, 2,424 surfaces, 112 on demand. The body of an item (`PlatformSource`, `DDSSource`, `MipMap n`, `DemandLoad` and so on, ids from 0x40 in the same table) is read by the item's own slot 2, not here.

## Quirks kept

* An item whose name the owner already knows is read and made, but not named here and never told it has loaded. The owner holds this database too, from the word `Texture`, so a name given twice in a file is "known" the second time.
* A list is reported as given twice only if the word `Texture` gave a non-zero count too. A list given twice leaves its first names unfreed; only the last are looked at.
* Read clears only if a surface count is set. Texture counts left with no surfaces and no list crash on null names, on both sides.
* The names' buffers come from the token file's heap (0x002C60B0), not the database's (0x002C62E4), which is used for the kept path.
* `Clear` frees `m_directory`; the destructor does not, nor clears anything but the base's fields.
* `Load` keeps the file's path when any item is on demand, and if a previous path was there and nothing cleared, it is overwritten unfreed.
* `Allocate` and the word `Texture` set counts, then `Init`, whose virtual `Clear` undoes them if a table is left from before.
* `FindFreeTexture` does not return until it finds an item with no levels: it makes more databases as it goes. +0x1D is 0 from new and at least 1 once read.
* Repeated `Texture`: reported, then `Init` clears everything read so far.

## Oracle

`python -I tools/oracle_run.py --suite agt`. All 579 distinct `.AGT` files, each loaded, loaded over itself, cleared, loaded again, under five states of what the owner knows; about 90 written texts for each word and error path under the same five states and two heap fills; `Allocate`, `Clear`, destructors, count, find along chains, push and pop, the owner's method, memory failures, no heaps, a file that will not open, a second file over a first, other paths. Result on 2026-11-06: `NO DIFFERENCE OBSERVED: 579 files, 2358 textures, 2424 surfaces, 112 on demand; 502261 comparisons, 0 differences`; 13/13 entries; positive control passes; `--mutate` fails; 187/187 source mutants detected (179 as a difference, 8 by a crash or hang). `verify.py --only` shows MATCH, MISMATCH or SIZE for each function and MATCH for the vftable. The mdb and mat suites, whose owner header changed by one declaration, still pass with no mutants; all 13 native tests pass on x64.

First mutant run 187/188. The survivor, removing the explicit `file.Close()`, is equivalent: the file's destructor calls the same Close on the next statement. It is dropped, with that reason beside the list. A mutant I had misnamed, "read after the lookup", only deleted the read; written properly it survived, because the test item never touched the names. A word no real file uses, `Tm2Source`, now makes the test item name itself as it reads, which shows the order.

Stand-ins, on both sides, so none of this is evidence about them: the items, whose reader here is the harness's and acts only on `DemandLoad` and `MipMap`; slots 2 to 13 of the database. The original's own code runs for everything recorded, and for the tokenizer, file code and name maps beneath it.

Crashes on both sides are compared as crashes, up to the crash: a file that will not open, no room for the path, stale counts, and a list before the word `Texture` (dividing by a table size of zero).

Not tested: counts too large to allocate, or negative; the real item classes (0x000312D0 and the concrete classes at 0x00289700 and beside it); the concrete database at 0x0028A6E0, including its real `MakeMore` at 0x001100D0; `NameSpace` given a name not a string reaches no difference in these runs but leaves stack bytes after any terminator, which only the first byte and hash could see. The caller at 0x0001A56A is not recovered.

On x64: `tests/native/test_agt.cpp` runs `Read`, `Allocate`, count, find and the name tables through the real text tokenizer. `Load` is not run on x64, for want of a test file system in that test.

## Mistakes of mine

* I read the `jbe` in 0x0001C730 as "continue when zero". It returns when zero: the function finds a free item, not a used one. My first source and first name for it were wrong. The oracle showed this as a hang in the original under my harness, which was built on the same misreading, and a watchdog thread, removed afterwards, gave the address. Renamed to `FindFreeTexture` and fixed.
* My first harness had that item's levels at 1 to end the search; same cause.
