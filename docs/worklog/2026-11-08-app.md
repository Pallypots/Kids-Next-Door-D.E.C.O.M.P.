# App: the game's main, start-up and the main loop (subsystem `gm/app`), 2026-11-08

For the integrator: this holds what belongs in docs/startup.md, docs/STATE.md and docs/verification.md. Reference build knd-xbox-usa-5454008a-v1. State of everything here:
Semantic-tested. A host MATCH from `tools/verify.py` says nothing about the original compiler (blocked, docs/toolchain.md).

**What a green result does not show, first.** Almost everything App calls is a double on both sides of the oracle: the SDK's memory query, the AtAp layer chain below
the atlas layer, the display, graphics, frameworks, scripts, save data, the sound volumes, the registry members of the .ADR work, and, among recovered code, the members
other suites check (settings' Load and ReadCommandLine, the mount manager's Mount/Unmount/list files, AtDatabaseLoader::Load, AtDataRegistry::Load, AtDataLibrary::Load,
GmManifestLoader's Configure and Update, the heap manager's CreateHeap/MakeEquivalent/DestroyHeap/Report, AtFormat, AtIoStream::SetHeap). So the oracle shows that App's
own logic agrees with the original's, call for call, argument for argument, over every byte of the App object and every global it writes. It does not show that start-up
works: nothing beneath those doubles runs here.

## Where a real build stops

`tests/native/test_app.cpp` runs `AppMain` on x64, synthetic and over a game directory (`test_app C:\KND\analysis-local\levels`, which holds `app.ini` and
`JamFiles\XBox\AppInit.JAM`), after setting up the recovered I/O context and mount manager over the host's files. Both stop at the same place:

    main stopped: App start-up: GlobalMemoryStatus (0x00085451, SDK) is not in this build

That is the first call of `GmApp`'s start-up (0x00141500), which is the first call of `App::Init`. No disc file is read before it. The order of what stops next, if each
seam in turn were supplied, read from the recovered code: 0x0009C3C0 (the AtAp layer chain below the atlas layer: user interface, cinema, scene, video, sound, controller,
graphics, kinematics, script, data management, math, I/O, network, event, base; this is where the devices, the memory system and the heaps are brought up); then in Init
0x00140350 (the derived mount manager), 0x0006C2A0/0x0006C3E0 (history logs), 0x0008DBA0 (display mode), App+0x5F90's slot 29 (the graphics database loader), then
App.ini through recovered code, 0x001416A0 (matrix device), 0x0008CFB0 (634 functions of subsystems), the game state's slots, 0x00090210, the three framework constructors,
then `LoadRegistries`, whose `Generic.ADR` would load through the recovered registry and stop at 0x00067D40. So a real build cannot reach the disc until the AtAp
chain exists: the chain is the next piece of start-up to recover, and the biggest.

  `GmLevelManager::FindLevel` 0x0008E420, `AtIoContext::PushPath` 0x00019370 and `PopPath` 0x000193A0, `GmScriptsInitNames` 0x000703B0, the heap setters 0x00083490,

* App's own slots: 0 `GetMemoryParams` 0x0008C620, 1 `CreateHeaps` 0x0008C860, 2 `DestroyHeaps` 0x0008C920, 7 `GetConfig07` 0x0008C680, 60 `GetAtlasConfig` 0x0008C830,
  64 `GetHeap` 0x0008C960, 67 `HeapsFree` 0x0008C9C0, 68 `HeapsUsed` 0x0008C980. The slots that are 0x001CC9F0 (an empty function) are empty inline here.

No vftable is claimed: App's has 69 slots and most are not recovered. `tools/verify.py --only` on the 28: 8 MATCH, 1 MISMATCH, 19 SIZE, none MISSING or UNRESOLVED.

`App()` is PARTIAL, not 0x0008E5B0: the bases (0x00141DA0 and the AtAp chain) are not recovered, so a host App has their members as zero and the unrecovered parts get
their seam classes' vftables. The App object is laid out flat at its x86 offsets (static_asserts), with the bases' members named where start-up touches them.

## Oracle (`tests/oracle/oracle_app.cpp`, suite `app`)

`NO DIFFERENCE OBSERVED: 32 inits (5347 calls logged on the original side), 38 runs of the loop (406 frames, 30 random), main; 16 crashes on both sides; 16007 comparisons, 0 differences`;
entries reached in every run: 28 / 28; `--mutate` fails as it must; positive control passes.

Mutants: **309 / 309 detected** (tests/oracle/suites/app.py; five dropped as equivalent, each with its reason there). The first run left three survivors, all
harness gaps: SetDefaults clearing m_quit was invisible because every case started with it clear, and Init's two all-levels mutants because the frameworks, shared
objects that Init writes, were not compared after Init. The SetDefaults case now starts with the flag set, and the frameworks are compared after every case.

Cases. Init: from different starting bytes; already running (Shutdown first); list files on; all levels on; five starting levels (found, missing, eight characters,
empty, a prefix); save types already 1, 4, 5, 6 and -1 (the unsigned test); the manifest done in 1, 2 and 5 slices; each registry file missing; no first heap; allocation
failing from the second, fourth, sixth and seventh push on; three data folders, one of eight characters; 48 MB left. The loop: quit before, the device's quit flag before,
no frames, plain frames, a scripted walk from the intro to the menu to the game, quit and the flag set mid-run, the one-shot at 0x003ADA50, and 30 random runs over random
tables and requests. The parts alone with more variation: memory sizes on both sides of 64 MB including above 2 GB, allocation failure at each push with and without
`App::s_heap`, all four combinations of registry files, the layer flag both ways, 40 heap configurations through CreateHeaps and DestroyHeaps, every pattern of missing
heaps for the free and used sums, GetHeap past the end and at 0x80000000 and -1, FindLevel over 14 names by 10 table lengths (including names with a terminator inside),
PushPath/PopPath over 0 to 3 file systems, past the eighth push and past the bottom. main with argc 0, 1, 2.

What is compared after each: the call log (every double logs its arguments; pointers into App as offsets, so both sides' Apps compare), the 0x6D4C bytes of App (the
manifest pointer only as made or not, being each side's own allocation), 33 globals at their original addresses against the recovered ones, the level manager and the
registry user each side has, the heap manager's override, and the frameworks' state after the loop. A slot no case should reach is counted and fails the run.

Not compared: the fields Init leaves uninitialised on the stack (`AtIoMountParams` +0x00, +0x08, +0x0C and `AppLogParams` +0x00), and the bytes past an eight-character
data folder, which the original hands over unterminated. 16 cases crash on both sides, all where the original crashes too: a mount manager that could not be allocated is
used straight after the report.

## Quirks of the original, kept

* GmApp's start-up takes 64 MB off the reported total when 64 MB or less is left, but the /LIMITMEM note prints the total as reported. The memory text goes only into a
  stack buffer: nothing prints it.
* `SetFrameworkTable` writes the same four values again when `TestAllLevels` is set, so the switch changes nothing there; Init's own test of it sets the intro's request
  to 2 instead.
* The framework table names a fourth framework (index 3: row 2 column 2, row 3 columns 0 and 1) that is never made. Moving to it would call through a null pointer.
* The loop sums frame times into a local capped at 300 ms, and never reads it.
* Init hands the mount manager the data folder from App.ini (slot 4) before reading the command line, so a data folder given on the command line does not reach it here.
* Init re-runs 0x000989D0 (recorded as the settings' constructor) on settings App's constructor already built with 0x00098160.
* `GmMoFramework::SetHeap` is called three times with the same heap; 0x000980F0 stores a heap nothing reads; of the twelve flags set at the end of Init, the object at
  0x003057C0 is skipped.
* `App::s_heapMemory` is 0x2280000, 1 MB more than the four heaps (0x2180000): the default heap of `GetMemoryParams`, whose region is that plus 0x2800.

## For docs/startup.md (corrections and additions)

* `App` RTTI: App : GmApp : AtApAtlasApplication, AtApUserInterfaceApplication, AtApCinemaApplication, AtApSceneApplication, AtApVideoPlayerApplication,
  AtApSoundApplication, AtApControllerApplication, AtApGraphicsApplication, AtApKinematicsApplication, AtApScriptApplication, AtApDataManagementApplication,
  AtApMathApplication, AtApInputOutputApplication, AtApNetworkApplication, AtApEventApplication, AtApBaseApplication. Constructor 0x0008E5B0, destructor 0x0008F130.
* Step 1: 0x00141500 is GmApp's start-up: the memory report, the audio options' defaults, then the AtAp layers' start-ups in a chain (0x0009C280 atlas, then 0x0009C3C0,
  each checking its own running flag, calling the next, asking App for its config by a slot, and initialising its layer object). 0x000703B0 makes the small-C scripts'
  name map; 0x00083490 and 0x00143DD0 store the first heap.
* Step 3: 0x0008CE00 makes the derived mount manager at App+0x6914 (0x00140350, vftable 0x0028DBA0), with App as its owner and App+0x31C as its context, and the history
  logs at App+0x68F0, and sets the stream heap. 0x0008DBA0 sets 640 by 480. 0x0008E240 loads `DataXbox\UI\DirtyDsk\loader` through App+0x5F90's slot 29, with the heap
  manager's override set to App's first heap. Init then gives the mount manager the App.ini data folder (slot 4) before reading the command line.
* Step 5: 0x001416A0 reads two things from the matrix device; 0x0008CFB0 is unrecovered and large; App+0x65B8 is FaAcPlayerGameStateData (slots 1, 3; slot 5 gets the
  Generic registry); 0x0008DC70 makes the three frameworks; 0x0008DDF0 the table of moves between them; 0x0008DEA0 loads `Design\Registry\Generic.ADR` into App+0x6950 and
  `Library.ADD` into App+0x6B40, each if present; 0x00139F10 reads the saved sound volumes; 0x00097EB0 is not identified.
* Step 7: 0x0008E420 is `GmLevelManager::FindLevel`, comparing eight characters.
* Step 8: the "SName" and "Title" strings go to 0x003050E8 and 0x003050F0; the script system (0x003B3418) is initialised and its callbacks registered (13, 5 for
  "Control", 31 for "SaveData"); both modules are enabled; a "Game" save type of 0xF8 bytes is registered with the space manager; the first framework is entered.
* Step 9: the loader is the level manifest on `PERSIST.MNG` (from the manifest work).
* **The main loop is 0x0008EBE0**, Init's second step, not 0x0008ED60. Each frame: the device's slot 6, the clock, App+0x692C's update, the scripts until done, a move
  between frameworks by the table, the framework's slots 3 and 2, then App's slot 39. 0x0008ED60 is App's slot 6, Shutdown, ending in a tail jump to SetDefaults.

  slot 2 in include/at/AtIoMountManager.h, non-pure with an inline body that stops, so the existing doubles deriving from it still compile, plus a declaration of AtFatal there.

* `GmAppAudioOptions` (include/gm/GmAppSettings.h) is App seen from 0x003B360C: its eight fields are App's +0x645C to +0x6478. App sets the pointer through
  `AudioOptionsView()`, which is `this` on x86 and shifted elsewhere so the fields still land on App's. It should be folded into App.
* The seams to AtDataRegistry (0x00067D40, 0x000675B0, 0x00066860, 0x000679E0) are members of that class for the .ADR work; `GmHistoryLogsConstruct` 0x0006C2A0 is
  `GmHistoryLogs`'s constructor (it sets `GmHistoryLogs::s_instance`).
* `AtSdkGlobalMemoryStatus` stops, as the brief asked of SDK calls. A port could answer it from the host, as platform/fatal.cpp answers the clock; that is a decision.

## Mistakes

* I first printed the reduced total in the /LIMITMEM note; the oracle showed the original prints the reported one.
* A comparison read random starting bytes as pointers into one side's App and reported false differences; only a difference is now looked at as a pointer.
* A double hashed the eight-byte data folder up to a terminator that is not there when the name is full, so it read stack past the buffer; it now reads eight at most.
* I sized `GmSaveTypes` without the word at 0x003051AC; a static_assert caught it.
* Shell patches with backslashes were mangled twice, as the lessons warn; I moved to the edit tool and to Python files written with the write tool.
