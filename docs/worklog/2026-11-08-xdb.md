# The Xbox texture and material databases (subsystem `at/xdb`)

Worktree branch, for the integrator. State: Semantic-tested. No byte match is claimed: the host compiler is not the original's. Names are inferred but two: `AtGrIPixelSurface` is the original's own, from its message `AtGrIPixelSurface: unsupported image format` in 0x00060430, and "Texture database" from 0x0028A698. Built on the concrete loader's branch (`worktree-agent-aad2323afa1a73246`, commit b1227b8), merged here with `--no-ff`; the merge needed no fixes.

## What a green result does not show, first

What a 2D texture does once read (its slot 12, 0x000FCAD0: it reads the image file and makes the Direct3D texture and its levels) and what a material does once read (its slot 0, 0x0010B7F0: it builds its stage states from the shader and textures) are the seam, `src/at/AtGrD3DTextureSeam.cpp`, and in the oracle they are the harness's on both sides. So are the device's calls those two reach and the release paths need: 0x000FB630 (a device stage lets go of a texture), 0x00205E20 (called before a texture is released; not known) and 0x00205D10 (a Direct3D resource's release). The oracle's doubles mark each object as the original's would leave it as far as release can see (a handle for the texture and each level's surface; every third load a chained surface with blocks and a palette; stage states with entries, blocks and the shared tables), so clearing and destroying are compared over loaded objects. Nothing of the pixels and nothing drawn is compared. 3D textures, cube maps and 3D surfaces are the seam classes on both sides: no `.AGT` on the disc lists one.

## Not recovered: what stops

* `src/at/AtGrD3DTextureSeam.cpp`, five functions, each stopping through `AtFatal` with the original's address: a 2D texture's slot 12 (0x000FCAD0), a material's slot 0 (0x0010B7F0), 0x000FB630, 0x00205E20, 0x00205D10. A test supplies them.
* In `src/at/AtGrD3DUnrecovered.cpp`: the palette's slots 1 to 10, the 2D surface's slots 6 to 13 (they lock, fill and copy pixels), the 2D texture's slot 11 (0x000FC8A0, makes the texture from a size and format) and slots 8 and 9 (0x000FC620, 0x000FC590). Slots 8 and 9 return a pointer, the texture and the first surface's palette, but the base declares them `int`; on a 64-bit host a pointer does not fit, so they stop, and `Texture()` and `PaletteOf()` do what they do. Retyping them is a shared edit (`AtTextureItem.h`, and the two `[symbols]` names in `config/functions.d/akc.toml`): requested below.
* 3D textures (0x001214A0, vftable 0x0028B88C), cube maps (0x00121730, 0x0028B8DC) and 3D surfaces (0x000FCD50, 0x00289738): classes with the original's sizes whose every body stops, the constructor first. No `.AGT` on the disc lists one (all 579 distinct files list only `Surface2D` and `Texture2D`).

## Quirks of the original, kept

* `TakeSurfaces2D` reports running out and hands out the surfaces past the end anyway; the report does not come back in the game.
* `MakeMore` and the material database's slot 3 copy the group's name with `AtCopyName8` into eight bytes of the frame: an eight-letter name space is passed unterminated. The mesh database's slot 8 (0x00111050) calls the same 0x00013F70 at 0x0011110D, into the same eight bytes; the loader's source and notes have `strcpy` into twelve bytes there. Only eight bytes reach a name space either way, so its oracle could not tell; noted for the integrator, not changed here.
* `Clear` of either database leaves `m_next`. Clearing a material database whose `OnReady` raised for memory and came back crashes, releasing material 0 of none (the oracle compares the crash).
* A 2D texture's `Release` keeps its owner and its surfaces; only its texture is cleared. `ClearPending` releases only when there are surfaces.
* A 2D surface's `Reset` releases its Direct3D surface but clears the pointer only at the end, after the palette and the base.
* `Surface2D`'s destructor and the base's are written out where the original inlines them; the palette's destructor here calls `Free`, which is the same code.
* The material's base constructor is called at 0x000383E0 and its destructor's body is 0x00038EB0: the same code twice. `AtMaterial.h` gives 0x00038EB0 as the constructor; I did not change it, but the integrator may want to record 0x000383E0.
